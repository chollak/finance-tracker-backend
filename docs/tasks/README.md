# Как устроена доска задач

`TASKS.md` в корне — единственный источник правды по текущей работе. GitHub Issues, Project и Wiki
могут содержать устаревшее январское планирование: обращаться к ним только когда задача явно просит
их сверить (например FT-049).

## Где что лежит

| Файл | Что внутри | Кто пишет |
|---|---|---|
| [`../../TASKS.md`](../../TASKS.md) | Задача в работе, очередь, список backlog | штаб |
| [`decisions.md`](decisions.md) | Лог решений, менявших направление; новые сверху | штаб, по решениям Шукура |
| [`backlog.md`](backlog.md) | Отложенные задачи с полными описаниями | штаб |
| [`archive/`](archive/) | Закрытые задачи с отчётами «Реализовано / Проверка» | при закрытии задачи, последним коммитом её PR |

Правило разделения простое: **в `TASKS.md` живёт только то, над чем идёт или пойдёт работа.**
Задача закрыта — её тело целиком переезжает в соответствующий файл `archive/`, а не остаётся с пометкой
`done`. Задача снята с очереди — переезжает в `backlog.md`, в доске от неё остаётся строка таблицы.

## Роли (с 2026-10-26)

- **Шукур** ставит цели и приоритеты, принимает продуктовые решения, делает то, что требует его рук
  (ПК, iPhone, BotFather, ключи, деньги, внешние аккаунты), и даёт «да» на правки своих настоящих данных
  (backfill). Остальное штаб мержит в `main` сам — Шукур так решил 2026-10-27.
- **Штаб** — один чат Claude Code верхнего уровня. Ведёт очередь и доску, запускает под-чаты, получает их
  отчёты, мержит PR и отчитывается Шукуру. Сам код не пишет. Штаб заменил Hermes: «QA by Hermes» в старых
  задачах теперь значит «под-чат проверки».
- **Под-чат разработки** — одна задача: своя копия репозитория (worktree) и ветка от `origin/main`, узкие
  TDD-срезы, `npm run verify`, PR в `main`. Не мержит и сам задачу не закрывает.
- **Под-чат проверки** — свежий взгляд на готовый PR, без контекста разработки. Сверяет PR с Definition of
  Done по пунктам, ищет баги и дыры в diff, сам гоняет `npm run verify`, для экранов снимает скриншоты.
  Отчёт — блокеры, серьёзные находки, мелочи и вердикт.

## Цикл задачи

1. **Выбор.** Штаб берёт из `TASKS.md` следующую задачу, у которой нет открытых вопросов, ручных шагов
   Шукура и незакрытых `Depends on`.
2. **Разработка.** Штаб запускает под-чат разработки. В брифе — номер задачи и где её описание, ветка от
   `origin/main`, TDD, `npm run verify`, PR в `main`; не мержить. Отчёт под-чата: ссылка на PR, что
   сделано, что нет и почему, результат `verify`.
3. **Проверка.** Когда PR готов, штаб запускает под-чат проверки. Тот берёт ветку PR в свою копию, сверяет
   каждый пункт Definition of Done, читает diff и проверяет PR на настоящем запуске — по разделу «Как
   проверяем». Бота проверяет сам штаб (там же).
4. **Правки.** Блокеры и серьёзные находки штаб отправляет в тот же под-чат разработки: у него есть
   контекст, правки идут в тот же PR. Потом проверка ещё раз. Мелочи в PR не обязательны: если они стоят
   того, штаб заводит их новой задачей в backlog.
5. **Закрытие на доске.** Последний коммит PR делает под-чат разработки по просьбе штаба: тело задачи
   переезжает в архив с разделами «Реализовано» (из своего отчёта) и «Проверка» (из отчёта проверки), строка
   задачи уходит из `TASKS.md`. Так доска в `main` меняется вместе с кодом. Архив: задачи вехи 10
   (FT-087…FT-143) — `archive/ft-087-143-pastel.md`, с FT-144 — `archive/ft-144-daily-use.md`.
6. **Мерж.** Штаб мержит сам, merge-коммитом (`gh pr merge --merge`), не спрашивая Шукура, когда выполнено всё:
   - `verify` на PR зелёный;
   - проверка не нашла блокеров и серьёзных проблем;
   - каждый пункт Definition of Done выполнен или явно перенесён в новую задачу;
   - миграция БД, если есть, проверена на копии настоящей базы (раздел «Как проверяем», пункт 5);
   - PR не правит настоящие данные Шукура (backfill вроде FT-108) — такое только после его «да».

   Мерж не трогает живой экземпляр: миграция применится, когда Шукур его обновит, и приложение сначала
   скопирует базу в `data/backups/`.
7. **Отчёт.** После мержа штаб коротко пишет Шукуру: что сделано, ссылка на PR, что проверить руками.
   Под-чаты задачи больше не нужны, их можно архивировать.

Правки только в документах доски (`TASKS.md`, `docs/tasks/`) штаб делает сам: PR и сразу мерж.

## Как проверяем

Каждый PR проверяется на настоящем запуске, а не только тестами. Проверка делает всё, что относится к задаче,
и прикладывает к отчёту доказательства: команды, ответы, скриншоты.

1. **Тесты.** `npm run verify` в копии ветки PR.
2. **API.** Сервер — конфигурация `api` из [`.claude/launch.json`](../../.claude/launch.json) (порт 3100, бот
   выключен). Запросы — `curl` с этой машины с заголовком `X-Dev-User-Id`. В отчёт — запрос и ответ.
3. **Экраны.** Конфигурации `api` и `webapp` (порт 5174, тестовый пользователь `900000143` без Telegram).
   Встроенный браузер, ширина 390 px, светлая и тёмная тема, рядом с доской из поля `Design`. В отчёт —
   скриншоты.
4. **Бот** — только штаб. Конфигурация `api-bot` в копии ветки PR, Telegram Web во встроенном браузере: Шукур
   входит туда один раз. Почему штаб: разрешение писать от аккаунта Шукура он дал в чате штаба. В Telegram Web
   открывать только чат бота из `dev.env` — остальные чаты не открывать и не читать.

   Пока живой экземпляр на маке, бот в `dev.env` тот же, что у живого: @FinanceTrackerDevBot (решение Шукура
   2026-10-27). Один токен опрашивает только один процесс: второй получит 409 и собьёт опрос первому. Поэтому:
   - проверки бота собирать и делать одним заходом;
   - перед заходом остановить живой экземпляр: `kill -TERM` процессу `scripts/dev-miniapp.js` из основной папки
     (`pgrep -fl dev-miniapp.js`) — он сам гасит сервер и туннель;
   - сообщения Шукура в это время уйдут в базу копии: записи в ней, которых штаб не отправлял, перечислить в
     отчёте — Шукур внесёт их заново;
   - после захода запустить живой снова из основной папки, во вкладке терминала приложения, чтобы процесс
     пережил чат: `<копия>/scripts/nvm-exec.sh npm run dev:miniapp -- --chat-id=131184740 --skip-build`. Готово,
     когда `curl localhost:3000/api/health` показывает `"telegramBot":{"state":"running"`. Туннель будет новый —
     кнопку меню помощник обновит сам;
   - в отчёте — с какого по какое время живой бот стоял.

   После переезда живого экземпляра на ПК (FT-159) у мака будет свой бот, и останавливать живой не придётся.
5. **Миграции.** На копии настоящей базы (`sqlite3 … ".backup …"` в `data/` копии ветки), никогда на самом файле.
   После запуска: `npm run migration:show` ничего не ждёт и не видит расхождений со схемой, число строк в
   затронутых таблицах до и после сходится. В отчёт — эти цифры.

**Node 22.** Команды `node` и `npm` — через `scripts/nvm-exec.sh` (например `scripts/nvm-exec.sh npm run verify`):
в PATH мака первым стоит системный Node 16, а без nvm под ним нет `fetch`, и сервер падает на старте.
Конфигурации `.claude/launch.json` уже идут через обёртку.

**Окружение копии.** Сначала `scripts/nvm-exec.sh npm ci` — ставит и webapp. Потом
`cp ~/.config/daftar/dev.env .env.local` — там ключ OpenAI и токен бота для проверок. Ключи в нём:
`OPENAI_API_KEY`, `TG_BOT_API_KEY`, `TG_BOT_USERNAME`, `WEB_APP_URL=https://dev.invalid`. Кнопкам Mini App в
Telegram нужен HTTPS, а для проверки бота важны ответы, а не кнопки. `.env.local` из основной папки в копию не
класть: в нём адрес туннеля и настройки живого экземпляра. Токен бота в `dev.env` пока тот же, что у живого,
поэтому сервер с ботом (`api-bot`) поднимается только по пункту 4. Конфигурации `api` и `webapp` бота не
запускают, им живой экземпляр не мешает. База копии — своя `data/`, пустая при первом запуске.

**Порты.** Тесты идут на 3100 и 5174: 3000 занят живым экземпляром, пока он на маке. На этих портах сервер
одновременно поднимает только один под-чат. Перед запуском проверить, что порт свободен; занят — дождаться.

**Что остаётся Шукуру** — проверки на телефоне: Mini App внутри Telegram на iPhone, Action Button, голос.
Штаб перечисляет их в отчёте после мержа.

## Итоговый отчёт

Когда очередь пройдена или штаб упёрся в остановку, он пишет Шукуру один итоговый отчёт:

| Задача | PR | Что проверено: verify · API · экраны · бот | Что проверить руками |
|---|---|---|---|

Следом — что не сделано и почему, что ждёт решения Шукура, и ключевые скриншоты.

## Параллельно

Две задачи идут одновременно, только если не трогают одни и те же файлы (видно по Context и Definition of
Done) и не зависят друг от друга. Не больше двух под-чатов разработки сразу. Перед мержем второго PR в него
подтягивается свежий `main` и `verify` гоняется заново.

## Когда штаб останавливается и спрашивает Шукура

- В задаче продуктовое решение или открытые вопросы.
- Нужен шаг руками Шукура: ПК, iPhone, BotFather, ключи, деньги, внешние аккаунты.
- PR правит настоящие данные Шукура (backfill, FT-108). Миграции схемы сюда не относятся: их штаб мержит сам
  после проверки на копии базы.
- `verify` красный после двух кругов правок, или проверка дважды подряд вернула блокеры.
- Конфликт с `main` меняет поведение, а не только текст.
- Всё из «Stop/ask before» в `CLAUDE.md`: деплой, Supabase, биллинг, политика лимитов, удаление веток,
  force-апгрейды зависимостей.

Пока ждёт ответа, штаб берёт задачу, которая от этого ответа не зависит.

## Статусы

Положение задачи в `TASKS.md` — основной признак состояния: раздел «В работе», «Очередь» или строка
в таблице backlog. Поле `Status:` уточняет детали внутри этого положения:

| Статус | Значение |
|---|---|
| `in_progress` | под-чат разработки работает прямо сейчас |
| `review` | PR готов, под-чат проверки смотрит его |
| `needs_fix` | проверка нашла блокер, задача вернулась в разработку |
| `blocked` | нужен ответ или решение Шукура |
| `backlog` | описана, но не запланирована |
| `done` | проверка подтвердила результат, PR смержен — задача уезжает в `archive/` |
| `cancelled` | потеряла смысл; причина и уцелевшие части записаны в теле |

## Правила

- Перед началом работы прочитать «Текущий фокус» в `TASKS.md`.
- Один под-чат разработки — одна задача.
- Без явного разрешения Шукура не делать force push, reset, удаление веток и файлов, деплой и применение
  внешних миграций БД.
- Задачи с продуктовым решением держать в backlog до явного решения Шукура.

## Формат задачи

```markdown
### FT-XXX: Короткое название на английском

Status: backlog
Priority: high | medium | low
Owner: Claude Code
Type: bug | feature | repo-hygiene | quick-action-ui | design-system | ...
Size: S | M | L
Depends on: FT-YYY (если есть)

Context:
Что не так и почему это важно. Ссылки на файлы и строки.

Definition of Done:
- [ ] Проверяемые пункты, а не намерения
```

При закрытии в тело дописываются разделы «Реализовано» (что и почему сделано именно так) и «Проверка» (что
реально запускалось и с каким результатом), после чего задача переезжает в `archive/` (см. «Цикл задачи», шаг 5).
