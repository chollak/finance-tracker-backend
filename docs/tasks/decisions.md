### 2026-10-26 — штаб и под-чаты вместо Hermes; штаб сам мержит код

Решение Шукура: работа идёт автономно из одного чата.

- **Как.** Один чат Claude Code верхнего уровня — штаб. Он ведёт очередь и доску и запускает под-чаты: под-чат
  разработки на каждую задачу (своя ветка от `origin/main`, TDD, `npm run verify`, PR) и под-чат проверки на
  готовый PR (свежий взгляд: Definition of Done по пунктам, diff, `verify`, скриншоты экранов). Сам штаб код не
  пишет. Цикл, параллельная работа и правила остановки — `docs/tasks/README.md`.
- **Hermes больше не нужен.** Его работу делят под-чат проверки (QA gate) и штаб (доска, мерж, отчёт). «QA by
  Hermes» в старых задачах значит «под-чат проверки». Роли в `CLAUDE.md` и `docs/tasks/README.md` переписаны.
- **Мерж кода — штаб сам**, merge-коммитом, если `verify` зелёный, проверка не нашла блокеров и серьёзных
  проблем, а Definition of Done выполнен. Почему: иначе очередь стоит на каждой задаче.
  **Уточнение 2026-10-27:** Шукур — «если всё ок, пусть сам заливает в main, я полностью доверяю». Штаб мержит и
  PR с миграцией БД: сначала её проверяют на копии настоящей базы (данные на месте, схема без расхождений).
  Мерж миграцию не применяет: она применится при обновлении живого экземпляра, после автоматической копии базы.
  «Да» Шукура нужно только на правку его настоящих данных (backfill вроде FT-108).
- **Доска меняется вместе с кодом.** Последний коммит PR переносит задачу в архив с «Реализовано» и «Проверка».
  Отдельных коммитов «задача в работе» нет. Правки только в документах доски штаб делает PR и сразу мержит.
- **Где автономия кончается.** Продуктовые решения и открытые вопросы; шаги руками Шукура (ПК, iPhone,
  BotFather, ключи, деньги); миграции и правки данных; `verify` красный после двух кругов; всё из «Stop/ask
  before» в `CLAUDE.md`. Под-чаты работают на маке: пока он спит, работа стоит. Облачные сессии не умеют
  отчитываться штабу, поэтому для штаба не годятся.
- **Проверка — на настоящем запуске** (уточнение 2026-10-27, по просьбе Шукура «всё сам тестировал, в конце
  чёткий результат»). Кроме `verify` — API через `curl` и экраны во встроенном браузере на тестовых портах 3100
  и 5174 из `.claude/launch.json`: 3000 занят живым экземпляром, пока он на маке. Тестовый пользователь входит без
  Telegram. Бота проверяет штаб через Telegram Web и только dev-бота: Шукур один раз входит в Telegram Web во
  встроенном браузере и даёт штабу разрешение писать dev-боту. Окружение копий — из `~/.config/daftar/dev.env`
  с токеном dev-бота, боевой `.env.local` в копии не попадает. В конце очереди штаб пишет итоговый отчёт: задача,
  PR, что проверено, что проверить руками на телефоне.
  **Уточнение 2026-10-27, позже:** второго бота пока не заводим — Шукур: «просто текущий используй для теста».
  В `dev.env` — @FinanceTrackerDevBot, тот же бот, что у живого экземпляра на маке. Один токен опрашивает только
  один процесс, поэтому на заход проверки бота штаб останавливает живой экземпляр и потом запускает снова
  (порядок — `docs/tasks/README.md`, «Как проверяем», пункт 4). Свой бот у мака появится при переезде на ПК (FT-159).

### 2026-10-26 — живой экземпляр на своём ПК (Windows + WSL) через Tailscale, не в облаке

Решение Шукура. Облачный вариант (Fly.io, около $4–5 в месяц) он отклонил: пользуется только он, запускать будет
локально.

- **Почему вообще.** Проверка 2026-10-26: продукт готов для ежедневного пользования, но живёт в `npm run dev:miniapp`
  на маке. Мак засыпает — бот молчит, итоги дня теряются (FT-144), адрес quick tunnel меняется при каждом запуске.
- **Где.** ПК с Windows + WSL, включён «как получится», не круглосуточно. Отдельная копия `~/daftar-live` на `main` со
  своей `data/` и `.env.local`: ветки разработки и их миграции не трогают живую базу. systemd-сервис с
  `Restart=always`; задача Планировщика Windows держит WSL запущенным — без неё WSL гасит дистрибутив, когда закрыт
  последний терминал, и сервис умирает. Мак — только разработка, с отдельным dev-ботом: два poller'а на одном токене
  дают 409, а две базы — двойные итоги дня.
- **Адрес.** `tailscale serve` → `https://<пк>.<tailnet>.ts.net`, виден только устройствам tailnet; Tailscale на iPhone
  включён всегда. Статичный IP `100.x` не годится: Telegram требует HTTPS с настоящим сертификатом. Заменяет
  Cloudflare quick tunnel: адрес постоянный, кнопка меню ставится один раз.
- **Бот — long polling.** Только исходящие запросы; пока ПК выключен, Telegram держит обновления до 24 часов. Webhook
  потребовал бы публичный адрес, а `WEBHOOK_MODE=true` сейчас только выключает бота.
- **База и бэкап.** SQLite в файловой системе WSL, не на `/mnt/c`. Раз в сутки systemd timer с `Persistent=true`
  (догоняет пропуск, если ПК был выключен) делает `sqlite3 .backup` в облачную папку Windows и хранит 30 копий. Копия
  вне WSL нужна, потому что весь дистрибутив — один файл `ext4.vhdx`. Живую базу в облачную папку не класть:
  синхронизация портит SQLite.
- **Быстрая запись с iPhone** (Action Button, потом iOS-приложение): токен, привязанный к владельцу, и
  `NODE_ENV=production` на живом экземпляре. Это решение по продовой авторизации Shortcut, отложенное 2026-09-04
  (FT-075). Почему не dev-режим: на живом экземпляре он включает заголовки разработчика и подробные ошибки. Почему не
  заголовки личности Tailscale (`Tailscale-User-Login`): вход навсегда привязался бы к Tailscale.
- **Закрытый доступ — `ALLOWED_TELEGRAM_IDS`.** Бот, API и рассылки — только для перечисленных. Tailscale закрывает API,
  но не бота: бот публичен в Telegram, лимиты free выключены (Д3), и любой нашедший тратит ключ OpenAI.
- **Обновление — одна команда вручную** (pull `main`, `npm ci`, сборки, перезапуск); копию перед миграциями делает
  приложение. Автообновление на домашнем ПК применяло бы миграции без присмотра. Мёртвый SSH-деплой на AWS
  (`deploy.yml`, `docker-cleanup.yml`) убирается; `verify.yml` и quality-gate остаются.
- **Мониторинг.** Внешний не нужен: ПК бывает выключен намеренно, алерты были бы шумом. При окончательном сбое
  polling процесс завершается, systemd его перезапускает; логи — journald.
- **iPhone.** Сначала Shortcut на Action Button → `POST /api/quick-capture` по адресу tailnet, без кода под iOS. Потом
  минимальное приложение «как SyncSpend» со своей очередью записей — она и решает «ПК включён как получится».
- **Не блокеры.** Старые маршруты с `userId` из тела и пути с 2026-10-21 отвечают 403 на чужой id, а API теперь виден
  только в tailnet; перевод на пользователя из авторизации — FT-162, вместе с FT-136. До переезда слить PR #91
  (FT-144, FT-145).

Задачи FT-153…FT-162 — в [`backlog.md`](backlog.md). Порядок: код FT-153, FT-154, FT-155 → живой экземпляр FT-156,
бэкап FT-157 → переезд FT-159 → Shortcut FT-160 → iOS-приложение FT-161; FT-158 и FT-162 — когда удобно. Остаются в
силе: решение 2026-08-13 (AWS и прод вне планов) и Д3 (лимиты free выключены).

### 2026-10-21 — на PR гоняется `npm run verify` вместо автоматического ревью Claude

Решение Шукура в локальной сессии.

- **Почему.** `claude-code-review.yml` на каждый PR запускал Claude с общим промптом, через секрет с подпиской.
  Ревью и так делают агенты после каждой задачи и Hermes; на большом PR общее ревью бесполезно; просроченный токен
  делал проверку красной и будил Auto-fix впустую. А тестов на PR не гонял никто: `quality-gate` в `deploy.yml`
  срабатывает только на push в `main`, и `main` не защищён.
- **Что.** `claude-code-review.yml` удалён; `.github/workflows/verify.yml` — `npm ci` и `npm run verify` на Node из
  `.nvmrc` для каждого PR. `@claude` в комментарии по-прежнему зовёт Claude (`claude.yml`).

### 2026-10-21 — пользователь только из авторизации; заголовки разработчика — только с этой машины

Найдено в локальной сессии при проверке запуска; сделано по поручению Шукура («что сможешь сам — делай»). Hermes
подтверждает при проверке.

- **Почему срочно.** `npm run dev:miniapp` открывает dev-сервер в интернет через quick tunnel, а адрес уходит в
  кнопках бота. Вне продакшена `X-Dev-User-Id` входил как кто угодно, `X-Shortcut-User-Id` без токена писал за
  кого угодно, `POST /api/transactions` писал за любой `userId` из тела вообще без входа, `guest_*` открывал
  маршруты без входа, а `verifyOwnership` пропускал UUID. Любой с адресом туннеля мог читать и менять записи.
- **Решение.** Заголовки разработчика действуют только для запроса с этой машины; Shortcut с телефона — только с
  `SHORTCUT_CAPTURE_TOKEN`. Гостей нет (Д4): `allowGuestMode` = `requireAuth`. Владелец записи — вошедший
  пользователь; `userId` в теле, если есть, должен быть им, иначе 403. `verifyOwnership` сравнивает строго.
- **По ревью безопасности.** `writeAsSignedInUser` сверяет `userId` и в пути, и в строке запроса (`?userId=` чужого
  пользователя в `POST /api/transactions` писал в чужой аккаунт). «Запрос с этой машины» требует ещё `Host` =
  localhost (от DNS rebinding) и допускает `X-Forwarded-For` только с loopback — прокси Vite теперь его ставит, и
  телефон по Wi-Fi через `vite --host` не проходит. Проверено вживую через настоящий туннель.
- **Что не трогали.** Старые маршруты с `:userId` в пути (бюджеты, долги, дашборд, подписка) остаются, но отвечают
  только своему пользователю. Мёртвые гостевые ветки удалит FT-136. Подробно — `docs/knowledge-base/01-architecture/
  auth-user-resolution-boundary-matrix.md`, раздел 2026-10-21.

### 2026-10-21 — FT-143: быстрый разбор берёт подпись, только если её слова называют одну категорию

Сделано в локальной сессии по поручению Шукура («что сможешь сам — делай»); Hermes подтверждает при проверке.

- Простая фраза «<подпись> <сумма>» остаётся без ИИ, только если подпись — целиком или своими словами — называет
  ровно одну видимую категорию расходов по правилу слов FT-138 (название, словарь, выученные слова). Запись идёт
  в эту категорию по её имени: «обед с командой 145к» → «Кафе» без «?».
- Незнакомое слово («стрижка 50000», «наушники 55$») и подпись, чьи слова называют две категории, идут к ИИ.
  Это меняет решение 2026-10-20 «Другое ?» для неузнанного слова: теперь «Другое ?» — только когда ИИ ответил
  ошибкой (нет ключа, сеть) **или не нашёл во фразе ни одной записи**. Второй случай добавлен сверх DoD: иначе
  простая фраза с суммой терялась бы целиком, хотя раньше записывалась.
- Скрытые категории правило не видит, как и автоматические пути записи (FT-099): подпись, которая называет только
  скрытую категорию, идёт к ИИ.
- По ревью: решает первый вид совпадения, который что-то нашёл. Сначала своё имя категории целиком («кофе» — в свою
  «Кофе», а не в стартовую «Кафе»), потом названия и словарь по словам, и только потом выученные слова: их пополняет
  каждое исправление каждого пользователя, поэтому словарь они не перебивают («кофе», выученное для «Продуктов»,
  остаётся «Кафе»).
- Известно и не исправлено: голые синонимы «яндекс», «yandex», «uber» у «Транспорта» уводят туда «яндекс еда» и
  «uber eats» без «?» (раньше было «Другое ?»); фраза с незнакомым словом при недоступном OpenAI ждёт таймаута SDK
  (по умолчанию долгого), прежде чем записаться в «Другое ?».

### 2026-10-21 — решения FT-133 (автономно)

- **Цель** — напоминает только «Вдвое меньше»: у «Отказаться» нет лимита, у подписки — своё напоминание. Один раз на
  80% лимита с дня ревизии и один раз сверх него; цель, сразу ушедшая сверх лимита, получает только второе сообщение.
  Пишет днём — 10:00–22:00 по часам пользователя («Днём» в листе «Цели и подписки»); пересёкшая лимит ночью — утром,
  пока цель считается. Превышение: «Лимит до конца октября превышен на 8 000 сум.», курсивом «Больше об этой цели в
  октябре не напишу.».
- **Подписка** — только когда нажато «Напомнить», в его день (накануне списания) с 10:00 до конца дня; без
  «Напомнить» бот молчит, иначе кнопка «Напомнить» ничего бы не значила. Сумма — последнее списание.
  «Отменено» = «Уже отменено» в приложении. «Оставить» — ревизия, где решили отменить, отмечает подписку «Нужно»,
  цель снимается; это и есть «снова попадёт в ревизию, только если подорожает» (правило FT-131), и работает, даже
  если та ревизия уже закрыта.
- **Ревизия** — бот зовёт только 1-го числа (с `auditTime` до конца дня) и только если есть траты на проверку; не
  дошло в тот день — зовёт приглашение на главной. «Позже» — назавтра в то же время, один раз, без «Позже», курсивом
  «Больше не напомню — ревизия ждёт на главной.»; день хранится в `notifications_log.due_on` (миграция). При
  выключенном «Звать на ревизию» «Позже» ничего не обещает; под зовом прошлого месяца только убирает кнопку.

  цели есть лимит и «Цели и подписки» включены.

### 2026-10-21 — решения FT-132 (автономно)

- **Ревизия — экран `/audit`** (`pages/audit`, данные — `entities/audit`), «Назад» — туда, откуда открыли (главная,
  «Ещё», аналитика), по прямой ссылке — на главную; «На главную» после итога возвращает на главную, не складывая её второй
  раз.
- **Отметка видна сразу** и сохраняется нажатием; отметки и «Готово» уходят по очереди, ответ сервера (вся ревизия)
  ложится под отметки, ещё не дошедшие. Не дошла — отметка снимается, Toast «Отметка не сохранилась». «Готово» ждёт
  ответа сервера: итог и цели считает сервер.
- **Главная** ждёт ревизию и цели вместе с остальными первыми чтениями (карточка не сдвигает записи). Приглашение — пока

- **«Мало данных»** честно по правилу FT-130: при записях с 12 октября первая ревизия — 1 декабря, строка «Записей пока —

- **Перенесённые траты** названы во вступлении («Ещё 1 — из ревизии августа») и в карточке («· за август»); в «следующую

### 2026-10-21 — решения FT-142 (автономно)

- **Заморозка состава** — колонка `audits.frozen` (миграция): её ставит первый `PATCH` кандидата (отметка или выбор
  цели) или «Готово», и снятая потом отметка её не снимает. Ревизии, сохранённые раньше, с отметкой, выбранной целью

### 2026-10-21 — решения FT-131 (автономно)

- **Ревизия** — ревизия прошлого месяца (по Ташкенту), открывается при первом `GET /api/audits/current` (позже — и
  напоминанием FT-133): кандидаты находятся тогда и хранятся как найдены, запись за тот месяц, добавленная потом,
  ревизию не меняет. Пока месяц не записан целиком (правило FT-130) — `too_early` с днём первой ревизии, строки нет.
  Менять можно только текущую ревизию: с 1-го числа прошлая закрыта (`409`).
- **Хранение** — `audits`: строка на пользователя и месяц, кандидаты с решениями JSON-колонкой `candidates` (как
  просит задача — «кандидаты и решения»), запись поверх прочитанной `version` с повтором: два нажатия сразу не теряют
  отметку. `goals`: строка на кандидата, ставшего целью.
- **Отметки сохраняются по нажатию** (`PATCH`), повторное нажатие снимает отметку, выбранное «Вдвое меньше /
  Отказаться» помнится. «Готово» — после первой отметки; первое даёт ревизии день, с него считаются все цели
  («Считаем с 14 октября — дня ревизии»), повторное после «Изменить отметки» день не меняет. После «Готово» цели
  следуют за отметками сразу.
- **Срок цели** — со дня ревизии до конца его месяца; следующая ревизия ставит цели следующего месяца, а главная в
  новом месяце снова зовёт на ревизию.
- **Неразобранное** приходит в ревизию следующего месяца один раз, со своими числами и причиной (`carriedFrom`),
  если правила не нашли ту же трату снова; оставленное снова не переходит дальше.
- **«Нужно»** не предлагается снова, пока трата не вырастет в 1,5 раза к месяцу, когда её отметили (подписка и
  тариф — пока не подорожают больше чем на 10%, как «Подорожала») — доска обещает «Предложим снова, только если
  трата заметно вырастет». **«Уже отменено»** — сервис не предлагается, пока его не спишут после этого дня.
- **Подписка**: следующее списание — через месяц от последнего в тот же день (31-е в коротком месяце — его
  последний день; годовая — через 12 месяцев), «Напомнить» запоминает день накануне списания (не раньше сегодня)
  для бота FT-133; ответ можно снять (`subscription: null`).
- **Числа**: лимит до конца месяца и траты по цели считают весь календарный месяц, как плитки главной и аналитика
  (FT-141); сравнение — с 1-го числа против тех же дней прошлого месяца; итог-план (`summary`) считает сервер.

### 2026-10-21 — ревью FT-129 (автономно)

- **«Отменить» во время отправки** скрывает запись сразу и помечает её в очереди на устройстве (`cancelled`), так что
  перезапуск её не вернёт. Отправка дошла — запись удаляется на сервере (`404` — уже удалена); ответа не было, `5xx`,

  раз не удаляется); сервер отказал (`4xx`) — убирается без «Запись не отправилась». Запись, отменённая, пока
  отправлялась другая, не уходит вовсе.
- **Связь возвращает только ответ самого сервера:** не `5xx` или JSON приложения (его `502`/`503` — тоже ответ).
  Страница шлюза — туннель Cloudflare с `502`, `503`, `504`, `52x` — связь не возвращает.
- **Подпись ждущей записи:** «Ждёт связи · проверьте сумму · Обед» — пометка сразу за меткой, чтобы многоточие её не
  срезало; одна «Ждёт связи · проверьте сумму» на 390px на 2px шире строки, поэтому подпись записи с пометкой может
  занять две строки (строка растёт), остальные — в одну. «Без заметки» у ждущей записи не пишется. Записи одной фразы в списке — в порядке фразы (общий момент
  фразы `writtenAt`, внутри — порядок отправки).
- **Ждущая запись не открывается** (Toast «Запись ждёт связи»), как и было; на доске она открывается. Это отличие
  записано в `design-vs-code.md` для QA Шукура: правка записи в очереди — отдельная задача, если она нужна.

### 2026-10-21 — решения FT-129 (автономно)

- **«Нет связи»** — событие браузера `offline`; ещё — запись, на которую сервер не ответил (15 с), и «Записывать без
  связи» под медленной загрузкой. Связь возвращает ответ сервера на запись или `GET /api/health` (раз в 15 с, мимо кеша
  service worker). Фраза, отправленная на разбор ИИ и оставшаяся без ответа, по-прежнему остаётся в поле: её `clientId`
  делает повтор безопасным, а разбор на устройстве после неё мог бы задвоить то, что сервер всё же записал.
- **Очередь** — Dexie (`daftar-offline`), запись с `clientId` уходит в `POST /api/transactions` по одной, по порядку:
  при `online`, на старте и раз в 15 с, пока что-то ждёт. Нет ответа, `401`, `408`, `429`, `5xx` — запись ждёт
  следующей попытки; другой `4xx` — убирается, Toast «Запись не отправилась · … — запишите её снова». Выход из аккаунта
  очередь не стирает: записи — пользователя, уйдут после входа.
- **Ждущая запись** — первой в «Последних операциях», её нельзя открыть до отправки (Toast «Запись ждёт связи»);
  «Отменить» убирает её из очереди, а уже отправленную удаляет на сервере. Остатки и плитки месяца считает сервер:
  ждущие записи в них не входят до отправки. Ручной ввод без связи пишет так же и возвращает на главную.
- **Разбор на устройстве** — как бот читает сумму (FT-122): части через запятую, «;», «и»; «к», «тыс», «млн», «$»,
  «usd», «долл», «сум»; «45» без единиц — 45 000 и «проверьте сумму» (пометка только в строке и Toast, в заметку записи
  не пишется). Две суммы в одной части — не разбирается. Категория — по первому слову из списка доски среди стартовых
  категорий (по `presetKey`), иначе «Другое» своего типа; доход — «зарплата», «пришло», «получил», «доход», «аванс».
  Доллары без видимого долларового счёта не пишутся: Toast «Нет долларового счёта».
- **Сохранённые чтения** — остатки, итоги месяца, последние записи, частые траты, категории, курс и настройки
  пользователя; заполняют пустые чтения без связи (и при старте без связи — ждём их до 1,5 с), не заменяя прочитанное в
  сессии. «Выйти» и потерянная сессия их забывают. Без связи главная не ждёт чтений, а ворота первого запуска пускают в
  приложение, если настроек на устройстве нет.
- **Голос и чек без связи** — экраны `/offline-voice` и `/offline-receipt` (ProblemScreen в виде `centered`), «Ввести
  вручную» открывает ручной ввод на их месте. В сети микрофон и камера по-прежнему говорят «скоро» до FT-117 и FT-134.

### 2026-10-20 — правила по ревью FT-123 (автономно)

- **Ответ суммой — одно правило для всех вопросов бота.** Голое число меньше 1 000 в сумах — тысячи и в ответе
  на «Сколько?» о доходе («кэшбэк» → «870» — 870 000 сум), как в «Сумму» с FT-122 и в `bareAmount` доски «Бот ·
  запись текстом и голосом»; бот говорит курсивом «"870" понял как 870 000 сум.», а «870 сум» пишет как есть. Во
  фразе малый доход остаётся как написан («кэшбэк 870»): там его называют вместе с суммой.
- **Ответ на «Сколько?» проверяет лимит записей** (при `FREE_LIMITS_ENABLED=true`): он добавляет запись. Вопрос
  остаётся открытым. «Сумму», «не 25, а 28» и ответ о крупной сумме лимит не проверяют — они меняют записанное.
- **Названное без суммы — тоже позиция фразы.** «нал», «$» и слова категории в «кофе 25к, такси нал» — не кофе:
  с одной ценой и одним пропуском фраза считается из двух позиций.

### 2026-10-20 — «Другое ?» для неузнанного слова (ревью FT-138)

Решено агентом по ревью FT-138: Шукур поручил решать такие вопросы самостоятельно; Hermes подтверждает при

- Решение «?» только для догадки ИИ (ниже) не говорило о быстром разборе без ИИ. Слово, которого нет ни в

## Обоснование вех 0 и 1

Веха 0 появилась после сквозного тестирования: редактирование транзакции и возврат из архива не работают вовсе, а суммы вида «12 млн» сохраняются как 12. Это ломает работу с данными раньше, чем начинаются вопросы к их интерпретации.

Веха 1 идёт следом: пока аналитика и бюджеты противоречат главному экрану, пользоваться продуктом как источником правды нельзя.
