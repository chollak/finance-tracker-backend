## Проблема

Finance Tracker разросся до 33 415 строк: 8 модулей, 44 use case'а, 13 страниц мини-аппа,
10 виджетов главной, Telegram-бот с командами, платежами и лимитами. При этом создатель
продукта им не пользуется.

Две названные причины:

1. **Трение на входе.** Вносить лень.
2. **Визуальная усталость.** На главной одновременно живут десять виджетов, четыре
   семантических цвета, и каждый блок оформлен скруглённой карточкой. Иерархии нет —
   глазу не за что зацепиться, и спустя время смотреть на это надоедает.

Обе причины ведут к одному исходу: продукт перестают открывать.

### Уточнение после чтения кода (2026-08-26)

Первоначальная версия этой спеки утверждала, что путь до записанной траты занимает семь
действий, включая обязательный выбор категории и подтверждение. **Это неверно.**

- `quickCategoryKeyboard` вызывается только из `commandHandlers.ts:92` и `:313` — это
  отдельная команда быстрого добавления, в голосовой поток она не входит.
- `CONFIDENCE_THRESHOLD = 0.6` в `messageHandlers.ts:316`: транзакция сохраняется всегда,
  подтверждающая клавиатура показывается только при низкой уверенности.

Фактический поток сегодня: сообщение → use case → сохранено → карточка с кнопками.
Это три действия, а не семь.

### Где источник трения на самом деле (замерено)

Первое подозрение пало на `getTodaySummary` (`messageHandlers.ts:346`), который на каждое
сообщение загружает всю историю транзакций пользователя ради двух сумм. **Замер это
подозрение снял:** 1,8 мс на сотне записей, 11,5 мс на тысяче, 72 мс на шести тысячах
против стабильных 3 мс при выборке по диапазону дат. Деградация линейна и реальна, но при
целевых 20–30 записях в месяц тысяча набирается за три года — одиннадцать миллисекунд
трением не являются. Скрипт: `scripts/measure-capture-latency.ts`, коммит `e2df093`.

**Настоящих источников два, и оба сетевые.**

`DATABASE_TYPE=supabase`, то есть каждое обращение к базе — round-trip, а не диск. До
первого ответа их набиралось около двенадцати, часть — дубли: `getOrCreateUser` звался
трижды за сообщение, причём в `telegramBot.ts:106` результат просто выбрасывался.
Заморозка учёта лимитов убрала два из них, остальные снимает фаза 1.

Главный вклад даёт вызов к OpenAI, и туда уходит **естественная речь**. Быстрый путь
разбора в `processTextInput.ts` глушат стоп-слова `за`, `по`, `и`, `купил`, `взял`, а
`COMPLEX_TEXT_MARKERS_PATTERN = /[.!?;]/` реагирует на любую пунктуацию — из-за чего
транскрипты Whisper не попадают в быстрый путь никогда. Проверено на корпусе:
«продукты 200 тысяч» разбирается мгновенно, «купил продукты на 200 тысяч» уходит в сеть.

Стоимость разбора бинарна: микросекунды или секунды, ничего между. Две визуально
одинаковые фразы дают несопоставимое время ответа, и непредсказуемость раздражает сильнее
стабильного ожидания.

**Отдельно найдена ошибка корректности.** В колонку `date` пишутся два формата:
`YYYY-MM-DD` в `processTextInput.ts:144` и полный ISO в быстром добавлении
`messageHandlers.ts:421`. Сравнение строковое, поэтому запись в формате ISO выпадает из
любой выборки по диапазону дат. В локальной базе одна строка из 29 уже испорчена.

## Решение в одном предложении

Сжать продукт до ядра захвата, вынести оркестрацию из Telegram-хендлера в use case
за одним контрактом, и переписать фронтенд заново под два экрана с явной иерархией.

## Принципы

1. **Захват — ядро.** Всё остальное обязано доказать, что служит захвату.
2. **Ядро одно, клиенты тонкие.** Telegram, будущий Shortcut и возможное iOS-приложение
   зовут один и тот же use case через один контракт.
3. **Замораживать, а не удалять.** Файлы остаются в репозитории, отключается регистрация.
   Возврат фичи — правка одного списка.
4. **Не строить того, чего не понимаешь.** Но собирать данные, чтобы понять позже.

### Механика заморозки

Заморозка выполняется отключением в трёх точках, без удаления файлов:

1. Сборка модулей — `src/appModules.ts`
2. Регистрация маршрутов — `src/delivery/web/express/expressServer.ts`
3. Навигация нового мини-аппа — просто не появляется

Отключаемое перечисляется **одним явным списком** с комментарием и датой заморозки, чтобы
спустя месяцы было видно: это решение, а не забытый мусор.

Тесты замороженных модулей остаются в прогоне. Они бесплатно охраняют код, который
предполагается вернуть, и сломаются раньше, чем о нём забудут.
`tests/productInvariants.test.ts` остаётся активным для живой части.

### Отдельно: почему заморожено обучение на исправлениях

`src/shared/application/learning/transactionLearning.ts` (280 строк) при разборе оказался
нерабочим. Петля «правка → паттерн → промпт» разорвана в трёх местах:

- мини-апп объявляет `originalText` и `originalParsing` в типах, но никогда их не отправляет,
  а контроллер без них тихо уходит на обычный update;
- рантайм-файла `data/patterns.json` не существует — есть только сид;
- фильтр `usageCount >= 2` в `getEnhancedPrompts` пропускает лишь один паттерн из трёх сидовых.

Плюс два дефекта замысла: в паттерн падают **все** слова длиннее двух символов (в сиде
«потратил», «деньги», «купил» стали ключевыми словами категории `restaurants`, что при
накоплении деградирует категоризацию), а сами паттерны общие на всех пользователей и
хранятся в файле на диске — это не переживёт второго инстанса.

Решение: заморозить целиком, ничего не чинить. Вместо этого — пассивный сбор данных
(см. модель данных), чтобы через месяц решать вопрос цифрами.

## Архитектура ядра

### Контракт

```
POST /api/capture
  { text?: string, audio?: File, source: 'telegram' | 'shortcut' | 'webapp' }
  → { transaction, confidence, lowConfidence: boolean }
```

### Use case

```
CaptureTransactionUseCase
  ├─ audio → TranscriptionService (Whisper) → text
  ├─ text  → ParsingService (GPT) → amount, category, type, merchant, confidence
  └─ CreateTransactionUseCase → repository
```

### Как клиенты добираются до use case

Существенное уточнение: Telegram-бот живёт в том же процессе, что и Express, и **не ходит
через HTTP**. Он вызывает `CaptureTransactionUseCase` напрямую, как обычную зависимость.

`POST /api/capture` — тонкая HTTP-обёртка над тем же use case, нужная мини-аппу сейчас
и Shortcut'у в будущем. Это не два пути и не две реализации: контракт HTTP описывает
ровно ту же операцию, что бот делает in-process.

```
Telegram handler ──┐
                   ├─→ CaptureTransactionUseCase → CreateTransaction → repository
POST /api/capture ─┘
```

### Что уже построено (уточнение 2026-08-26)

Ядро существует. `ProcessTextInputUseCase` и `ProcessVoiceInputUseCase` — это и есть
описанный выше `CaptureTransactionUseCase`: они разбирают вход (быстрый путь без OpenAI,
фолбэк на GPT для сложных фраз), создают транзакцию и уже проставляют `originalText`,
`originalParsing`, `confidence`, `needsReview`, `semanticType`.

HTTP-контракт тоже существует: `POST /api/voice/text-input` и `POST /api/voice/voice-input`
в `voiceProcessingController.ts` — с авторизацией (`allowGuestMode`), рейт-лимитом
(`aiRateLimiter`), резолвом telegramId → UUID и валидацией аудио через multer.

Telegram-хендлер оркестрацию **не делает** — он вызывает use case (`messageHandlers.ts:165`).
Предметная логика уже отделена от доставки.

Следствие: отдельный `CaptureTransactionUseCase` и отдельный маршрут `/api/capture`
писать не нужно. Переименование существующих маршрутов ради красоты контракта —
это работа без результата для пользователя, и в этот отрезок она не входит.
Мини-апп и будущий Shortcut используют существующие `/api/voice/*`.

## Поток захвата

Выбранный вариант — «парсер решает, показывает, даёт поправить»:

1. Голосовое сообщение или текст боту
2. Транзакция **сохраняется сразу**, всегда
3. Бот отвечает карточкой: сумма, категория, кнопка `[поменять]`
4. Бездействие означает подтверждение. Тап на «поменять» открывает inline-выбор категории

**Подтверждения нет ни при какой уверенности.** Это осознанный отказ: подтверждающий шаг
стоит одно лишнее действие ради ошибок в меньшинстве случаев. Низкая уверенность
не блокирует запись, а помечает её флагом и подсвечивает в ленте.

Шаги 1–3 уже работают именно так. Меняется только ветка низкой уверенности:
`transactionConfirmationKeyboard` уходит, остаётся `transactionAutoSavedKeyboard`,
а `CONFIDENCE_THRESHOLD` влияет лишь на подсветку в карточке, не на набор кнопок.

## Модель данных

Из трёх полей, задуманных как новые, два **уже есть** в `Transaction`: `originalText`
и `confidence` (а также `originalParsing`, `needsReview`, `merchant`, `semanticType`).

Действительно новое — одно поле:

| Поле | Тип | Назначение |
|---|---|---|
| `source` | `'telegram' \| 'shortcut' \| 'webapp'` | откуда пришла запись |

Новая таблица `corrections` — пассивный лог правок:

```
id, userId, transactionId, field, oldValue, newValue, originalText, createdAt
```

Ничего не читает и ни на что не влияет. Единственная цель — через месяц ответить
цифрами на вопрос «как часто парсер ошибается и стоит ли строить обучение».

**Кто пишет в лог.** `UpdateTransactionWithLearningUseCase` заморожен вместе с
`transactionLearning`, поэтому запись в `corrections` вешается на обычный
`UpdateTransactionUseCase`: он сравнивает пришедшие поля с текущими и на каждое
изменившееся пишет строку. Один путь правки — и из мини-аппа, и из inline-кнопки бота, —
поэтому лог наполняется независимо от того, откуда пришло исправление.

### Миграции

Три новых поля транзакции и таблица `corrections` требуют миграций **в обеих базах**.
Для SQLite — через изменение entity (в разработке действует `synchronize: true`).
Для Supabase — SQL-миграция в `migrations/`. На момент написания Supabase на паузе,
и миграции 007/008 к нему не применены: перед новой миграцией нужно разобраться
с этим накопленным долгом, иначе порядок применения разъедется.

**Приватность.** `originalText` — персональные данные: люди диктуют «занял у Азиза»,
«аптека, лекарства». В логи не выводится, при отладке не печатается.

## Фронтенд

Мини-апп пишется **заново**, отдельным проектом. Существующие ~16 000 строк в `webapp/src`
остаются в git и не используются.

### Что переносится без изменений

Авторизация через Telegram WebApp — валидация `initData`, хендшейк с бэкендом, гидратация
пользователя (`app/providers/UserInitializer.tsx` и связанное в `shared/api`). Причина: этот
код отлаживается только на живом телефоне через туннель, циклами по несколько минут.
Переписывание означало бы заплатить за уже пройденную отладку второй раз.

### Структура

Плоская, без Feature-Sliced Design:

```
src/
  pages/       — 2 файла
  components/  — ~8 файлов
  api/
  lib/
```

Слои вводятся тогда, когда появляется боль от их отсутствия, а не заранее.
Для двух экранов шесть слоёв FSD означали бы папки с одним файлом внутри.

### Экраны

**Главный.** Три зоны: сумма за месяц крупной цифрой, столбики по дням за последние
семь дней, лента транзакций сгруппированная по дням. Плюс кнопка добавления.

**Правка транзакции.** Сумма, категория, сохранение.

**Добавление — пересмотрено 2026-08-27.** Кнопка на главном открывает **форму**
сгруппированным списком: описание, сумма, категория, дата. Рядом остаётся быстрый путь —
одна строка естественным языком, которая уходит в разбор.

Первоначально спека предписывала обратное: только одно текстовое поле, без формы. Решение
изменено после того, как создатель продукта поработал с SyncSpend на своём телефоне и
предпочёл форму. Аргумент против формы — «второй независимый путь создания транзакции» —
остаётся верным и никуда не делся: он теперь оплачивается сознательно (см. «Цена решения»).

**Поля формы — ровно те, что существуют у продукта.** Поля «способ оплаты» из SyncSpend
нет: счетов и карт в системе не существует, и заводить поле значило бы обещать сущность,
которой нет.

**Сумма без дробной части.** SyncSpend показывает `UZS0.00`, но у сума копеек на практике
нет, а число и так достигает тринадцати знаков с разделителями.

### Цена решения

1. **Возвращается `POST /api/transactions`.** Быстрый путь идёт в `/voice/text-input`,
   где авторизация есть. Форма — это ручное создание, то есть тот самый эндпоинт, который
   планировалось заморозить за полное отсутствие авторизации. Его придётся **чинить, а не
   прятать**: `allowGuestMode` + `resolveUser` + проверка владения.
2. **Два пути создания вместо одного.** У формы своя валидация и свой набор полей.
   Именно из-за расхождения двух путей уже был баг `f0ce281`. Смягчение: оба пути обязаны
   сходиться в `CreateTransactionUseCase`, где стоит нормализация даты и семантического
   типа, и ни один не имеет права писать в репозиторий мимо него.
3. **Форма не заполняет `originalText`.** У записи, созданной вручную, исходной фразы нет,
   и лог правок по ней ничего не скажет о качестве парсера. При анализе данных из задачи 3
   фазы 3 такие записи надо отделять — по полю `source`.

### Компоненты

`SummaryCard`, `WeekBars`, `TransactionRow`, `DayGroup`, `AddButton` — и три поля
на экране правки.

### Принципы визуала

Причина усталости от текущего дизайна — не цвета и не шрифт, а отсутствие иерархии:
десять равнозначных виджетов, четыре семантических цвета, всё в скруглённых карточках.
Когда всё одинаково важное, всё одинаково неважное.

Новый визуал строится от иерархии: три зоны вместо десяти, монохром плюс один акцент,
одна крупная цифра-герой, остальное отступает в серый.

### Ограничитель для графика

Недельные столбики считаются **одним запросом** — суммы по дням за последние семь дней.
Без `DashboardModule`, без `financial-health`, без настраиваемых периодов и работы
с часовыми поясами.

График в этом отрезке декоративен: без установленного бюджета он не отвечает на вопрос
«много или мало». Он оправдан тем, что даёт петлю обратной связи — записал трату, увидел
сдвиг. Как только для него потребуется что-то большее, это сигнал размораживать бюджеты,
а не наращивать аналитику.

в фазу не входит — вместо него ставится счётчик, чтобы решать по данным, а не на глаз.

Фаза 4 — Shortcut и токен-авторизация — начинается только когда появится постоянный
хостинг, и требует отдельной спеки. В этот отрезок не входит.

---

## Риски

**Заморозка сгниёт.** Отключённый код перестанет собираться после пары рефакторингов.
Смягчение: тесты остаются в прогоне и сломаются раньше, чем о коде забудут.

**Мусор в базе из-за отказа от подтверждений.** Риск принят осознанно.
Предохранитель — подсветка низкой уверенности в ленте.

**Объём работ по фронтенду.** Полное переписывание мини-аппа — самая тяжёлая фаза.
Смягчение: перенос авторизации без изменений, всего два экрана.

**Расхождение документации.** `docs/knowledge-base/10-design-guidelines/design-system.md`
описывает текущие токены и 37 UI-примитивов и станет неправдой. Переписывается вместе
с кодом в фазе 2. `docs/VISION.md` и `CLAUDE.md` также требуют правки — список готовых
фич и описание модулей перестанут соответствовать действительности.

---

## Чего в этом отрезке нет

iOS-приложение, виджеты домашнего экрана, Apple Shortcuts, постоянный хостинг,
обучение на исправлениях, бюджеты, долги, аналитика, подписки, монетизация.

## Допущения, требующие подтверждения

1. **Пассивный лог правок включён в фазу 3.** Предложен как условие того, что отложенное
   решение об обучении останется дешёвым. Явного согласия не было.
2. **Авторизация Telegram переносится как есть**, а не пишется заново. Возражений не
   поступило, но и подтверждения тоже.
3. ~~**Добавление в мини-аппе — одно текстовое поле, а не форма.**~~ **Снято 2026-08-27.**
   Допущение оказалось неверным: создатель продукта предпочёл форму, поработав с SyncSpend
   на своём телефоне. См. «Добавление — пересмотрено» и «Цена решения».
4. **Заморозка не ломает интеграционные тесты.** Если существующие тесты собирают
   приложение целиком и ожидают все восемь модулей, отключение регистрации их уронит.
   Проверяется в первый же день фазы 0; при необходимости замороженные модули собираются
   для тестов, но не подключаются к маршрутам.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Что есть ядро | Захват сейчас, ясность потом |
| Где живёт захват | API-ядро, Telegram и Shortcut — тонкие клиенты |
| Судьба остальных фич | Заморозка (скрыть, не удалять) |
| Момент захвата | Парсер решает, показывает, даёт поправить |
| Обучение на исправлениях | Отложить, сначала измерить |
| Хостинг | Локально сначала, публичный адрес потом |
| Главный экран | Сумма + недельный график + лента |
| Старый фронтенд | Новый webapp с нуля |
| Структура фронтенда | Плоская, без FSD |
