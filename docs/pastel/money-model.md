# Модель денег: счета, валюты, курс, переводы

Это единственная часть переноса, которую нельзя сделать «перекраской»: дизайн опирается на сущности,
которых в базе нет. Документ — проект схемы и миграции для фазы 2 из [tasks.md](tasks.md). Названия колонок —
предложение; окончательные выбирает задача.

## Правила из дизайна

1. Итог на главной = сумма видимых счетов; доллары пересчитаны по действующему курсу, курс всегда назван.
2. Валюты только две: сум и USD.
3. Переводы, обмены и корректировки не попадают в расходы, доходы, аналитику, итоги дня и цели.
4. Обмен хранит фактический курс сделки; смена курса потом прошлое не меняет.
5. Счёт скрывают, а не удаляют: он выпадает из итога и выбора, его записи остаются в истории и аналитике.
6. Валюту счёта можно сменить, только пока у него нет операций.
7. Любое удаление — с отменой: мягкое удаление и восстановление.
8. В сумах дробей нет; у USD — центы.

## Суммы

- Все суммы хранятся целыми в сотых долях: `*_minor bigint` (тийины для сумов, центы для USD). Одна шкала
  для обеих валют — меньше ветвлений. Сумы на вводе целые, поэтому дробных тийинов не появится.
- `decimal(10,2)` и арифметика `number` с `Math.round(x*100)/100` уходят. В домене — помощник `Money`
  (сложение, сравнение, форматирование) без плавающей точки.
- В Postgres `bigint` приходит строкой — нужен transformer TypeORM. В JS целые безопасны до 9·10¹⁵ тийинов,
  то есть до 90 трлн сум.
- **Переходный период.** Запись принимает и `amountMinor`, и старое `amount` (сумы числом) и переводит
  второе в первое. Иначе сломаются писатели, которые ещё не переписаны: quick-add бота,
  `CreateTransactionUseCase`, записи долгов, PUT с обучением (новые записи с FT-113 пишет ручной ввод, а
  правит с FT-115 карточка операции — обе в `amountMinor`; `TransactionForm` удалена). Ответы содержат оба
  поля. `amount` удаляется в уборке (FT-136).
- Бюджеты не трогаем: они уходят из интерфейса (решение Д2), их `decimal` остаётся как есть.

### Пересчёт долларов в сумы

Как в прототипе: по **действующему курсу на момент показа**, с округлением до целых сум и знаком «≈» там,
где в сумме есть доллары. Отдельно пересчитанную сумму у записи не храним. Следствие: итоги прошлых месяцев
с долларами слегка меняются вместе с курсом — поэтому они и помечены «≈». Обмены от этого не зависят:
у них свой курс сделки.

## Остаток счёта

```
остаток = opening_balance
        + Σ доходы − Σ расходы        (записи счёта с date ≥ opening_date)
        + Σ входящие перемещения − Σ исходящие   (с date ≥ opening_date)
```

- В остаток входят **все неудалённые и неархивные записи по `type`**, независимо от `semanticType` и
  `needsReview`: деньги ушли со счёта, даже если категорию ещё проверяют. Аналитика, наоборот, фильтрует по
  `semanticType` и не берёт `needsReview`.
- Записи раньше `opening_date` в остаток не входят, но остаются в истории и аналитике. Так мигрированная
  история не ломает остаток, а экран первого запуска просто задаёт начальный остаток на сегодня.
- Остаток считается на чтении, без кэша: объёмы маленькие. Станет медленно — добавим кэш.

## Миграция существующих данных

Перед каждым шагом — копия `data/database.sqlite`. Каждый шаг — отдельная миграция TypeORM с проверкой после.

1. **Суммы.** `amount_minor = round(amount × 100)` построчно; проверка — та же формула по каждой строке и
   совпадение сумм по пользователю.
2. **Категории.** Каждому пользователю 8 + 8 стартовых. Старые id и русские названия (включая значение по
   умолчанию `'Другое'`) переводятся по таблице ниже **с учётом `type` записи**: `transfer`, `debt` и
   неизвестное → «Другое» того же типа. Перенести также обучение (`data/patterns.json`,
   `data/learning-data.json`) и кнопки `quickadd:<id>` бота. `budgets.categoryIds` не трогаем (Д2).
3. **Счета.** Каждому пользователю — счёт «Карта» (UZS); вся история переезжает на него;
   `currency = 'UZS'`. Начальный остаток и его дату задаёт первый запуск.
4. **Первый вход после обновления** открывает «Сколько у вас сейчас денег?» (FT-109) — до новой главной.
   Введённые суммы становятся начальными остатками на сегодня; история до этой даты в остаток не входит и не
   переписывается.
5. **Прежние переводы.** Все старые записи — `semanticType = expense`: backfill из FT-045 не применялся.
   Значит, прошлые переводы себе и снятия наличных сейчас считаются расходами. Применять ли backfill —
   решение Д7 и задача FT-108. Новые переводы создаются уже перемещениями.
6. **Архив.** Архивные записи (`isArchived`) и дальше исключены отовсюду — из истории, аналитики и остатка.
   Вкладки «Скрытые» в дизайне нет, вернуть их можно только из базы (решение Д7).

## Что меняется в API

Новые маршруты берут пользователя из авторизации, без `:userId` в пути. Сейчас `/voice/*` и
`/quick-capture` доверяют `userId` из тела запроса — в новых маршрутах так не делаем.

| Маршрут | Назначение | Задача |
|---|---|---|
| `GET/PATCH /api/settings` | тема, уведомления, свой курс, счёт по умолчанию, первый запуск | FT-098 |
| `GET/POST/PATCH /api/categories` | категории пользователя | FT-099 |
| `GET /api/accounts`, `POST`, `PATCH /api/accounts/:id` | счета с остатками, итог, действующий курс | FT-101 |
| `GET /api/rates/usd` | курс ЦБ, свой курс, какой действует | FT-102 |
| `POST /api/moves`, `DELETE /api/moves/:id`, `POST /api/moves/:id/restore`, `GET /api/accounts/:id/operations` | перевод, обмен, корректировка; операции счёта | FT-104 |
| `POST /api/transactions/:id/restore` | отмена удаления | FT-105 |
| `GET /api/transactions?q&categoryIds&accountIds&type&from&to&cursor` | история; заменяет мёртвый админский `GET /api/transactions` | FT-107 |
| `GET /api/analytics?month=YYYY-MM&type=expense` | аналитика с честным сравнением | FT-120 |

Ввод (`quick-capture`, голос, бот) учится выбирать счёт: «нал», «наличными» → «Наличные»; «картой»,
«uzcard», «humo» → «Карта»; «$», «долл», «usd» → долларовый счёт; иначе — счёт по умолчанию. Ответ разбора
говорит, что предположено (`assumptions`): тысячи, категория, счёт.
