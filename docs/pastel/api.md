# API вехи 10

Маршруты, которые добавляет фаза 2 (модель денег). Схема и правила — [money-model.md](money-model.md).
Документ растёт вместе с задачами: каждая задача дописывает свои маршруты.

## Общие правила

- **Пользователь — только из авторизации.** Заголовок `Authorization: tma <initData>` (вне production —
  `X-Dev-User-Id: <telegram id>`); в браузере без заголовка — httpOnly-cookie сессии, которую подтвердил бот
  (FT-128, «Вход в браузере через бота»). Ни путь, ни query, ни тело не задают, чьи это данные. Middleware
  `createCurrentUserMiddleware` переводит Telegram id во внутренний UUID и создаёт пользователя при первом
  обращении. Без авторизации — `401`.
- **Ответ** — как у всего API: `{ success: true, data, timestamp }`; ошибка — `{ success: false, error: { code, message } }`
  с кодом `400` (валидация), `403`, `404`, `409`, `500`.
- **Суммы** — целые в сотых долях: `*Minor` (тийины для сумов, центы для долларов). Старые маршруты
  на переходный период принимают и `amount` в сумах, а отвечают обоими полями (FT-097).
- **Даты** — `YYYY-MM-DD`; моменты времени — ISO 8601.

## Записи: суммы (FT-097)

`POST /api/transactions`, `PUT /api/transactions/:id`

| Поле | Что |
|---|---|
| `amountMinor` | целое, ≥ 1, ≤ 100 000 000 000 (1 млрд в сумах или долларах) |
| `amount` | старое поле, сумы числом; переводится в `amountMinor` |

Можно прислать одно из двух или оба; оба должны совпадать, иначе `400 amount and amountMinor disagree`.
Записи в ответах содержат `amountMinor` и `amount`.

## Записи: заметка (FT-113)

`POST /api/transactions`: `description` — заметка, необязательна (ручной ввод сохраняет без неё). Нет поля,
`null`, пустая строка или одни пробелы — запись с пустой заметкой. Не строка или длиннее 500 символов — `400`.

## Записи: категории (FT-099)

`POST /api/transactions`, `PUT /api/transactions/:id` принимают категорию двумя способами:

| Поле | Что |
|---|---|
| `categoryId` | id категории пользователя (`GET /api/categories`). Чужой — `404`; другого типа, чем запись, — `400` |
| `category` | старое поле: старый id (`taxi`), название (`Кафе`, без учёта регистра) или синоним (`кофейня`). Неизвестное — «Другое» того же типа |

В ответах у записи `categoryId`, `category` — **текущее название** категории и `categoryColor` — её цвет
(для старых экранов, FT-100). Новым экранам название и цвет брать из списка категорий по `categoryId`.

Даты записей — день по Ташкенту: если писатель прислал полный момент (`2026-10-15T22:30:00Z`), сохраняется
`2026-10-16`.

Смена `type` без новой категории переносит запись в одноимённую категорию другого типа («Другое» → «Другое»)
или в его «Другое». Ввод текстом и голосом выбирает только из видимых категорий.

## Записи: счёт (FT-101)

`POST /api/transactions` и `PUT /api/transactions/:id` принимают `accountId` — один из видимых счетов
пользователя. Без него запись идёт на счёт по умолчанию (`defaultAccountId` в настройках, иначе первый
видимый). Скрытый счёт — `400`, чужой — `404`. В ответах у записи `accountId`.

## Записи: валюта и источник (FT-103)

| Поле | Что |
|---|---|
| `currency` | `UZS` или `USD`; сумма записи — в этой валюте. Без поля: валюта выбранного счёта, без счёта — `UZS` |
| `source` | откуда запись: `telegram`, `miniapp`, `ios_shortcut`, `receipt`, `manual`. Пишет сервер; у `POST /api/transactions` всегда `manual` |

- **Валюта записи = валюта счёта.** `POST` с `accountId` и другой `currency` — `400`. Без `accountId`, но с
  `currency: USD` запись идёт на долларовый счёт (по умолчанию, если он долларовый, иначе первый видимый
  долларовый); если долларового счёта нет — `400`.
- **`PUT`:** смена `accountId` проверяет валюту записи (`currency` из запроса или прежнюю) против валюты
  нового счёта — не совпала → `400`. Одна смена `currency` без смены счёта — `400`: деньги не меняют
  валюту на месте, их переносят на счёт нужной валюты.
- **Ввод текстом и голосом** (`quick-capture`, бот, `/voice/*`) сам выбирает счёт и валюту по словам:
  - «$», «долл…», «usd», «бакс…» — доллары; иначе сумы;
  - счёт, названный в тексте («с Humo»), — он; «нал», «наличными», «кэш» — счёт вида «наличные»;
    «картой», «uzcard», «humo» — вида «карта» (из подходящих — сначала счёт по умолчанию);
    иначе — счёт по умолчанию. У переводов, накоплений и снятия наличных ни вид, ни названный счёт не
    учитываются: «перевёл 500 000 на Humo» называет, куда пришли деньги, а не откуда ушли — счёт по умолчанию;
  - во фразе с несколькими записями («кофе 25к налом и подписка 9.99$») у каждой записи своя валюта и
    свой вид счёта из разбора, а не слова всей фразы; названное без суммы — тоже позиция («кофе 25к, такси
    нал»: «нал» — такси, кофе — на счёт по умолчанию, FT-123);
  - «кофе 45» — 45 000 сум: целое число меньше тысячи без «к», «тыс» и «сум» читается как тысячи — только
    у расходов: мелкий доход бывает настоящим («кэшбэк 870»);
  - **долларов без долларового счёта** запись не теряет: сохраняется в USD на счёте по умолчанию с
    `needsReview: true`. В остаток сумового счёта она не входит, пока её не перенесут на долларовый.
- **Догадки разбора** — в ответе `quick-capture` и голоса у каждой записи `assumptions` (с FT-114 там же
  `categoryId` и `amountMinor` записи — по ним экран проверки показывает и меняет её):

```json
[
  { "kind": "thousands", "written": "45", "amount": 45000 },
  { "kind": "category", "name": "Кафе" },
  { "kind": "account", "name": "Наличные", "reason": "hint" },
  { "kind": "currency", "currency": "USD", "reason": "no_usd_account" }
]
```

`account.reason` — `hint`, если счёт выбран по словам, `default` — если по умолчанию. Подтверждение (`ack`)
пишет сумму в валюте записи: «Наушники · 55,00 USD».

**Без суммы** (FT-123): то, что фраза называет без суммы («такси» в «кофе 25к, такси, обед 45»), не
записывается — в ответе `quick-capture` и голоса оно лежит в `withoutAmount` (`description`, `category` по
названию из разбора, `type`, `date`, `paymentKind`). Бот спрашивает «Сколько?» и записывает его с суммой ответа
тем же путём, что и фразу (`captureWithAmount`): «такси 18к нал» — счёт по слову, «18» — «понял как 18 000».

**Догадка о категории** (`kind: "category"`, FT-138, решение 2026-10-20) — категория, которую не назвало ни
одно слово записи: та, что ИИ выбрал сам, и «Другое» для незнакомого слова, которое ИИ не смог прочитать. Её нет, если
категорию дали слова записи:

- **название категории пользователя** — «кафе», «Кофейни» у переименованной;
- **слово словаря категорий** — название, id и синонимы старых категорий, которые вошли в стартовую
  (`presetSynonyms`: «кофе», «такси», «продукты», «evos»), в том числе с другим коротким окончанием
  («продуктов», «обедали»: основа от 4 букв, после неё не больше 3 букв — «обеденный» уже другое слово);
  целыми словами — «чай» не находится в «случайно». Только как написаны — «оплата», «дорога», «другое»,
  «курсы»: их основа начинает обиходные слова другого смысла («оплатил», «дорого», «другу», «по курсу»).
  Голых брендов многих услуг — «яндекс», «yandex», «uber», «убер» — в словаре нет (FT-150): «яндекс плюс» —
  подписка, «uber eats» — еда; «Транспорт» дают «яндекс такси» — словом «такси» — и целиком «yandex go»,
  «яндекс го». Подсказкой промпта ИИ синоним с брендом не бывает: с «яндекс го» у «Транспорта» ИИ уводил туда же
  «яндекс плюс»;
- **выученный паттерн** — из `patterns.json` (а пока его нет — из поставляемого `patterns.seed.json`), те же
  паттерны, что видит промпт ИИ: от 2 применений; паттерны общие, по ключу стартовой категории. Считаются
  псевдонимы мерчантов с категорией («uzum market») и те слова паттернов категорий, что указывают на неё
  (`namingWordsOf`): не общие слова о деньгах и времени («купил», «потратила», «деньги», «вчера», «для» —
  список `GENERIC_WORDS` в `categoryGuess.ts`), не голый бренд — ни слово паттерна, ни псевдоним мерчанта
  («яндекс», «убер»; `BARE_BRANDS`, FT-150; «yandex go» считается; промпт ИИ его тоже не показывает), не слова
  короче 3 букв и с цифрами («25к») и не слово, которое есть в паттернах двух категорий. Поэтому «купил шаурму
  35к», которую ИИ отнёс к «Кафе», — «Кафе ?», хотя в поставляемом паттерне «Кафе» есть «купил».

Слова записи: у фразы из одной позиции — вся фраза; у фразы из нескольких (с названными без суммы) — слова фразы, которые есть в заметке
или мерчанте, что ИИ дал этой записи, в том числе с другим окончанием (заметка «продукты» — слово фразы
«продуктов»); слово, дописанное ИИ, — «Покупки на Uzum» — не считается.

Быстрые разборы без ИИ берут категорию из слов, поэтому то же правило. Простая фраза «<подпись> <сумма>»
остаётся без ИИ, только если подпись — целиком или своими словами — называет **ровно одну** видимую категорию
расходов пользователя (FT-143): «такси 18000», «кино 80000» (старые «Развлечения» → «Другое»), «обед с командой
145к» → «Кафе» — без догадки. Решает первый вид совпадения, который что-то нашёл: своё имя категории целиком («кофе» —
в свою «Кофе», не в «Кафе»), затем названия и словарь по словам, затем выученные слова — они словарь не перебивают. Иначе фраза идёт к ИИ, как сложная: слово, которого нет ни в названиях, ни в словаре
(«стрижка 50000», «наушники 55$», голый бренд «яндекс 20000», «uber eats 120000»), и подпись, слова которой
называют две категории («кофе продукты 50000»). Если ИИ
ответил ошибкой (нет ключа, сеть) или не нашёл во фразе ни одной записи, запись пишется как раньше — в «Другое» с
догадкой «Другое ?» (решения 2026-10-20 и 2026-10-21, `docs/tasks/decisions.md`); сложная фраза при ошибке ИИ
по-прежнему не записывается. Переводы, накопления и снятие наличных быстрый разбор кладёт в «Другое» по виду
записи — без догадки. Голос — всегда ИИ, правило то же.

По этому правилу «?» показывают все: проверка записей — чип «Кафе ?»; подтверждение одной записи (`ack`;
бот присылает его на каждую запись) — «Uzum · 180 000 сум · Покупки?», а если заметка и есть название
категории — «Покупки? · 180 000 сум». Вопросы бота с кнопками — «Записал в «Покупки» — верно?», а у
«Другое ?» — «Категорию не узнал» — FT-123.

Экраны, которые ещё складывают `amount` сами (сегодняшний итог, итоги дня в истории, сводка в «Ещё»),
долларовые записи пока не складывают с сумами, а считают «не в счёт»; бюджеты (уходят, Д2) их не учитывают.

## Удаление и восстановление записей (FT-105)

`DELETE /api/transactions/:id` удаляет запись мягко: ставит `deleted_at`. Ответ —
`{ message, id }`. Удалённая запись пропадает отовсюду — история, остатки, аналитика, бот,
выгрузка, обучение: репозиторий по умолчанию читает только неудалённые. Изменить удалённую нельзя (`404`).

`POST /api/transactions/:id/restore` возвращает запись (`200`, запись целиком). Повтор для неудалённой записи
ничего не меняет; неизвестная или чужая — `404`.

Счётчик бесплатного лимита записей: удаление его уменьшает, восстановление увеличивает — один раз.

## Повтор из офлайн-очереди (FT-106)

`POST /api/transactions` и `POST /api/quick-capture` принимают `clientId` — id, который клиент сам
даёт записи: латиница, цифры и «-», до 64 символов (UUID подходит). Уникален в паре с пользователем.

- **`POST /api/transactions`.** Первый раз — `201` как обычно. Повтор с тем же `clientId` новую запись
  не создаёт и отвечает `200` с прежней: `{ id, transaction, repeated: true }`. Если её успели удалить —
  она в ответе с `deletedAt`. Тело повтора не сравнивается: запись — та, что пришла первой.
- **`POST /api/quick-capture`.** Записи одного захвата получают `<clientId>`, `<clientId>:1`, `<clientId>:2`…
  Повтор текст не разбирает заново (ИИ не вызывается) и отвечает записями первого раза по порядку,
  удалённые — с `deletedAt`, и `repeated: true`. Чего в базе нет — названия счёта и догадок (`assumptions`) —
  в ответе на повтор нет.
- Два одинаковых запроса одновременно создают одну запись: второй упирается в уникальный индекс и
  отвечает записью первого.
- Неверный `clientId` — `400`. Без `clientId` всё как раньше: каждый запрос — новая запись.
- **Время ввода (FT-175).** `POST /api/quick-capture` принимает и `capturedAt` — когда фразу набрали на телефоне
  (ISO 8601 с секундами и поясом). Записи ложатся днём ввода по календарю пользователя, «вчера» — днём раньше него.
  Не больше 5 минут вперёд и не старше 30 дней, иначе `400`. Повтор с тем же `clientId` отвечает записями первого
  раза при любом `capturedAt`. Контракт — [`QUICK_CAPTURE_API.md`](../QUICK_CAPTURE_API.md#time-of-input-capturedat).
- **Webapp (FT-129).** Записи без связи (кнопки трат, ручной ввод, простой текст, разобранный на устройстве) ждут в
  очереди Dexie со своим `clientId` и уходят в `POST /api/transactions` по одной, по порядку, когда связь вернулась;
  запись, на которую сервер не ответил (сеть, 15 с без ответа), остаётся в очереди и уходит снова с тем же `clientId`.
  `4xx` (кроме `401`, `408`, `429`) — запись убирается из очереди и Toast «Запись не отправилась». Есть ли сервер,
  webapp спрашивает `GET /api/health` (service worker его не кеширует). «Отменить», нажатое во время отправки: запись
  остаётся в очереди помеченной, после ответа удаляется `DELETE /api/transactions/:id` (повтор `clientId` отдаёт её
  `id`, даже удалённую — тогда второго удаления нет; `404` на удаление — уже удалена).

## История: поиск и фильтры (FT-107, FT-116)

`GET /api/transactions?q&categoryIds&accountIds&type&from&to&cursor&limit` — записи текущего пользователя,
новые сверху: по дате, затем по времени создания, затем по id. Заменяет прежний админский список всех записей.

| Параметр | Что |
|---|---|
| `q` | до 100 символов, правило [`SearchField.md`](components/SearchField.md) (FT-116). Без учёта регистра и «ё» по-русски: «такси» находит «Такси». Запрос делится на слова и цифры: **каждое** слово должно найтись в заметке или магазине (колонка `search_text`), в **текущем** названии категории (после переименования запись находится по новому имени) или в названии счёта; все цифры вместе — начало суммы в целых сумах или долларах: «25 000» находит кофе за 25 000, но не зарплату 12 500 000. Знаки, пробелы, точки и запятые разделяют слова; `%` и `_` ищутся как текст |
| `categoryIds`, `accountIds` | id через запятую или повтором параметра, до 50 |
| `type` | `income` или `expense` |
| `from`, `to` | `YYYY-MM-DD`, включительно; `from` не позже `to` |
| `limit` | 1–100, по умолчанию 50 |
| `cursor` | `nextCursor` прошлой страницы |

```json
{
  "items": [ { "id": "…", "amountMinor": 2500000, "category": "Кафе", "…": "…" } ],
  "nextCursor": "WyIyMDI2LTEwLTE2Iiwi…",
  "summary": { "count": 2, "netMinor": -10900000, "usd": { "present": false, "missingRate": false } }
}
```

`summary` (FT-116) — всё, что нашли поиск и фильтры, на всех страницах: строка «2 операции · −109 000 сум» под
чипами истории. Есть только на первой странице (без `cursor`) запроса с `q`, `categoryIds`, `accountIds`, `type`,
`from` или `to`; иначе `null`. `netMinor` — в сумах: доходы плюс, расходы минус, какой бы ни был `semanticType`;
доллары — по действующему курсу пользователя, каждая запись с округлением до целых сум. `usd.present` — были
доллары (сумма приблизительная, «≈»); `usd.missingRate` — курса нет, доллары в `netMinor` не вошли.

Удалённые и архивные записи в историю не попадают. `nextCursor: null` — последняя страница. Ошибка в
параметрах — `400`; без авторизации — `401`. Записи, сохранённые до FT-100 с полным моментом в `date`
(«2026-10-14T05:30:00.000Z»), фильтруются по своему дню и листаются как остальные.

## Итоги за период (FT-103)

Доход, расход и разбивку по категориям считает один сервис — `PeriodTotalsService`
(`summarizePeriod`). Через него идут `GET /api/transactions/analytics/summary/:userId`, разбивка и топ категорий,
дашборд, итоги дня бота и `/today` (FT-124: `GetPeriodTotalsUseCase.forPeriod`); `/month` и
строка о месяце в итогах — через аналитику месяца (FT-120), то есть тот же сервис.

- Всё в сумах. Доллары — по действующему курсу пользователя (свой курс, иначе ЦБ), с округлением до
  целых сумов; долларовые записи никогда не складываются с сумами как есть. Если курса ещё нет,
  долларовые записи в итог не входят, а в результате `usd.missingRate: true`; внутри сервиса `leftOutUsd`
  считает такие записи по тому, чем они были бы (расход, на проверке) — для «· 2 записи» в итогах бота (FT-124),
  в ответ `GET /api/transactions/totals` не попадает.
- Расход — только записи с `semanticType: expense` и доход — `income`, без ожидающих проверки
  (`needsReview`). Ожидающие проверки — отдельно (`needsReview.count`, `totalMinor`). Переводы, накопления,
  снятие наличных, долги и возвраты — отдельно (`excludedMovements`) и в доход/расход не входят.

`GET /api/transactions/totals?from&to` (FT-111) — итоги текущего пользователя за период через тот же сервис:
плитки месяца на главной и строка-вывод под балансом. Пользователь — только из авторизации.

```json
{ "from": "2026-10-01", "to": "2026-10-31", "incomeMinor": 1629500000, "expenseMinor": 768440000,
  "netMinor": 861060000, "recordCount": 42, "needsReview": { "count": 1, "totalMinor": 4500000 },
  "excludedMovementsMinor": 50000000, "usd": { "present": true, "missingRate": false, "rateMinor": 1265000 } }
```

| Поле | Что |
|---|---|
| `from`, `to` | обязательны, `YYYY-MM-DD`, включительно; `from` не позже `to` |
| `incomeMinor`, `expenseMinor`, `netMinor` | в сумах (тийины), правила выше; удалённые и архивные записи не читаются |
| `needsReview` | ожидающие проверки: сколько и на какую сумму — в доход и расход не входят |
| `excludedMovementsMinor` | переводы себе, накопления, снятие наличных, долги и возвраты |
| `usd` | были ли доллары, хватило ли курса (`missingRate`) и по какому курсу пересчитаны |

Ошибка в датах — `400`; без авторизации — `401`.

## Аналитика (FT-120)

`GET /api/analytics?month=YYYY-MM&type=expense|income` — куда ушли (или откуда пришли) деньги за месяц, с честным
сравнением (правила — `design-system.md`, раздел «Аналитика»). Пользователь — только из авторизации; без неё — `401`.
`month` — по умолчанию текущий (день по Ташкенту), позже текущего или не `YYYY-MM` — `400`; `type` — по умолчанию
`expense`, другое значение — `400`.

Считает сервис итогов (FT-103): доллары — по действующему курсу пользователя, одному для обоих периодов; ожидающие
проверки (`needsReview`), переводы, накопления, снятие наличных, долги и возвраты не входят; удалённые и архивные
записи не читаются; перемещения (`/api/moves`) — не записи и сюда не попадают. Записи, сохранённые до FT-100 с
полным моментом в `date`, считаются по своему дню: с FT-120 так читает период любая выборка по датам (итоги главной,
частые траты, старая аналитика, бюджеты) — раньше такая запись выпадала из последнего дня периода.

- **Периоды.** Текущий месяц сравнивается с теми же днями прошлого, по сегодняшний: `1–14 октября` против
  `1–14 сентября` (короткий месяц — до своего конца). Записи текущего месяца — весь календарный месяц, как у плиток
  главной (FT-141): запись с датой позже сегодня в этом месяце входит в сумму, поэтому `period.to` — последний день
  месяца, а подпись «1–14 октября» экран строит по `today`. Прошлый месяц — целиком против всего предыдущего. Доходы
  текущего месяца — против всего прошлого месяца. `wholeMonth` — период — целый законченный месяц; текущий месяц
  целым не бывает. `firstMonth` — месяц самой ранней записи (удалённые и архивные не считаются): раньше него
  сравнивать не с чем (`previous: null`, «Первый месяц учёта»), назад листать некуда; `currentMonth` — дальше
  листать некуда.
- **Первые 7 дней учёта** (от дня первой записи, сегодня включительно; седьмой день их заканчивает) — ни
  сравнения, ни вывода: `firstDays: { days: 3, daysLeft: 4 }` (иначе `null`) и
  `insight: { kind: "too_early", days: 3, daysLeft: 4 }` («Пока записи за 3 дня — выводы через 4 дня»).
- **`comparable`** — есть прошлый период, в нём есть суммы этого типа и первые 7 дней прошли. Иначе
  `previousTotalMinor`, `change` и у строк `previousMinor`, `previousCount`, `change` — `null`: строки показывают долю.
- **Строки** (`categories`) — по сумме за период; категории только из прошлого периода — в конце, с суммой 0.
  `sharePercent` — целые проценты, вместе ровно 100 (лишние пункты получают наибольшие дробные части). `hasUsd` —
  внутри пересчитанные доллары: «≈». Скрытые категории остаются.
- **Изменение** (`change`): `up` / `down` с `percent` («↑ 40%», «↓ 15%»), `same` — округлилось до 0% («как было»),
  `new` — в прошлом периоде не было («новое»). Доходы незаконченного месяца не «падают»: меньше, чем за весь
  прошлый месяц, — `so_far` с долей прошлого месяца («пока 60%») или `not_yet` («пока нет»). `diffMinor` — разница
  со знаком: «на 714 400 сум больше».
- **Вывод** (`insight`), правило — `ANALYTICS_RULES` в `src/modules/transaction/domain/monthAnalytics.ts`. Расходы —
  только категории от 3 операций в обоих периодах; доходы — любые: доход приходит редко (зарплата раз в месяц),
  как на доске «Аналитика · доходы». Сначала самый большой рост — `change` с `direction: "up"` («Кафе: на 312 000 сум
  больше, чем за 1–14 сентября») или `new`, если раньше категории не было («Фриланс: 3 795 000 сум — в сентябре не
  было»); нет роста — самое большое снижение (`direction: "down"`), кроме доходов незаконченного месяца. Ни того ни
  другого или сравнивать не с чем — `largest`: самая большая доля («Больше всего — продукты: 29% расходов»). Пустой
  месяц — `null`.

```json
{
  "month": "2026-10", "type": "expense", "today": "2026-10-14", "currentMonth": "2026-10", "firstMonth": "2026-08",
  "period": { "month": "2026-10", "from": "2026-10-01", "to": "2026-10-31", "wholeMonth": false },
  "previous": { "month": "2026-09", "from": "2026-09-01", "to": "2026-09-14", "wholeMonth": false },
  "firstDays": null, "comparable": true, "totalMinor": 768440000, "hasUsd": false, "previousTotalMinor": 697000000,
  "change": { "kind": "up", "percent": 10, "diffMinor": 71440000 },
  "categories": [
    { "categoryId": "…", "name": "Кафе", "amountMinor": 109200000, "count": 10, "sharePercent": 14, "hasUsd": false,
      "previousMinor": 78000000, "previousCount": 9, "change": { "kind": "up", "percent": 40, "diffMinor": 31200000 } }
  ],
  "insight": { "kind": "change", "categoryId": "…", "name": "Кафе", "direction": "up", "diffMinor": 31200000,
    "amountMinor": 109200000, "previousMinor": 78000000 },
  "usd": { "present": false, "missingRate": false, "rateMinor": null, "source": null }
}
```

`usd` — доллары среди показанных записей (этого типа, в периоде или в том, с которым сравнивают): курс и откуда он
(`cbu` — ЦБ, `own` — свой) для сноски «Доллары пересчитаны по курсу ЦБ: 1 USD = 12 650 сум»; `missingRate` — курса
нет, доллары не вошли.

`GET /api/analytics/categories/:id?month=YYYY-MM` — одна категория пользователя, скрытая тоже; чужая или
неизвестная — `404`. Тип берётся у категории, `month` — как выше. Поля периода (`month`, `today`, `currentMonth`,
`firstMonth`, `period`, `previous`, `firstDays`, `comparable`, `usd`) — как у месяца: `firstDays` говорит экрану
категории, что сравнения нет из-за первых дней, а не из-за первого месяца. Плюс:

| Поле | Что |
|---|---|
| `category` | `{ id, name, type }`; цвет — из `GET /api/categories` |
| `amountMinor`, `count`, `sharePercent`, `hasUsd` | как строка категории месяца: доля — во всех расходах (доходах) месяца |
| `previousMinor`, `change` | сравнение по правилам месяца: «↑ 40% к 1–14 сентября · на 312 000 сум больше» |
| `days` | каждый день периода: `{ date, amountMinor, count, hasUsd }` — столбцы «По дням»; доллары без курса не входят. У текущего месяца — все дни месяца: после сегодня пусто, кроме записей с будущей датой |
| `records` | операции категории за период — те, что вошли в сумму, и доллары без курса, — новые сверху: по дню, времени записи, id |

Вывод про саму категорию («Больше половины — «Семейный ужин» и «Ужин с друзьями»») экран строит из `records` (FT-121).

## Частые траты для чипов (FT-114)

`GET /api/transactions/frequent` — частые траты текущего пользователя для чипов над полем ввода на главной.
Пользователь — только из авторизации; без неё — `401`.

Правило — константа `FREQUENT_RECORDS_RULE` (`src/modules/transaction/domain/frequentRecords.ts`): до 6 самых
частых пар «категория + заметка + сумма» за последние 30 дней (с сегодняшним, день по Ташкенту), каждая — от
3 повторов. Заметка сравнивается без учёта регистра, «ё» и лишних пробелов; суммы разных валют — разные траты.
Считаются только настоящие расходы: без доходов, переводов, накоплений, снятия наличных, долгов, ожидающих
проверки (`needsReview`), удалённых и архивных. Порядок — по числу повторов, при равенстве — свежее раньше.

```json
{ "items": [ { "categoryId": "…", "note": "Кофе", "amountMinor": 2500000, "currency": "UZS", "accountId": "…", "count": 7 } ] }
```

`note` — как записано в последний раз; `accountId` — счёт последней из этих записей. Пустой `items` — частых
трат нет: новичку главная показывает 4 стартовых чипа из прототипа (Кофе 25 000, Такси 18 000, Обед 45 000,
Продукты 150 000).

## Счета (FT-101)

`GET /api/accounts` — все счета пользователя (скрытые тоже) с остатками и итог. Пользователю без счетов
создаётся «Карта» (UZS).

```json
{
  "accounts": [
    { "id": "…", "name": "Карта", "kind": "card", "currency": "UZS", "openingBalanceMinor": 0,
      "openingDate": "2026-10-16", "openingAt": "2026-10-16T05:12:40.118Z", "isHidden": false, "sortOrder": 10,
      "balanceMinor": 12345600, "userId": "…" }
  ],
  "totalMinor": 12345600,
  "rate": { "rateMinor": 1285000, "source": "cbu", "date": "2026-10-16" },
  "missingRate": false
}
```

| Поле | Что |
|---|---|
| `balanceMinor` | в валюте счёта: `openingBalanceMinor` + доходы − расходы с `openingDate` (+ перемещения, FT-104). Учитываются все неархивные записи по `type`, какой бы ни был `semanticType` и даже на проверке; записи раньше `openingDate` не входят, а в день `openingDate` при заданном `openingAt` — и записанные до этого момента (FT-163) |
| `openingAt` | момент, когда первый запуск ввёл остаток (FT-163), ISO; `null` — день открытия входит в остаток целиком (счёт добавлен позже, стартовая «Карта», первый запуск до FT-163) |
| `totalMinor` | сумма **видимых** счетов в сумах; доллары — по действующему курсу, с округлением до целых сум |
| `rate` | курс, по которому пересчитаны доллары (FT-102); `null`, если видимых долларовых счетов нет или курса ещё нет |
| `missingRate` | `true`, если долларовый счёт не вошёл в итог, потому что курса нет |

`POST /api/accounts` — `{ name, kind: "cash"|"card", currency: "UZS"|"USD", openingBalanceMinor?, openingDate? }`
→ `201`. «Сколько на нём сейчас» — начальный остаток на дату открытия (по умолчанию сегодня), не доход.

`PATCH /api/accounts/:id` — любое из `{ name, kind, currency, isHidden }`. С новой валютой можно прислать
`openingBalanceMinor` — остаток, введённый заново в этой валюте (FT-118, «Изменить» на экране счёта: «Валюта
меняется — введите остаток в новой валюте»); дата открытия не меняется. Без смены валюты (одно поле или та же
валюта) `openingBalanceMinor` — `400`: расхождение остатка правится корректировкой («Сверить остаток»).

`DELETE /api/accounts/:id` (FT-118) — «Отменить» сразу после «Счёт добавлен». Удаляет только счёт, которого не
касалась ни одна запись и ни одно перемещение, удалённые тоже → `200 { id }`. Счёт с операциями — `409`: его
скрывают («Скрыть, а не удалить»). Последний видимый счёт — `400`, чужой — `404`.

## Первый запуск (FT-109)

`POST /api/accounts/opening-balances` — экран «Сколько у вас сейчас денег?».

```json
{ "cashMinor": 125000000, "cardMinor": 318000000, "usdMinor": 42000 }
```

| Поле | Счёт | Что |
|---|---|---|
| `cashMinor` | «Наличные», `cash`, `UZS` | сколько сейчас, в тийинах; нет поля — 0 |
| `cardMinor` | «Карта», `card`, `UZS` | то же |
| `usdMinor` | «Доллары», `cash`, `USD` | в центах |

- Каждая сумма становится начальным остатком своего счёта **с датой сегодня** (по Ташкенту) и моментом
  `openingAt` — тем же, что `onboardedAt`: записи и перемещения раньше этой даты в остаток не входят, но остаются
  в истории и аналитике. Сегодняшние, записанные до первого запуска (бот, Shortcut), тоже не входят — введённая
  сумма их уже учитывает (FT-163); записанные после — входят. На экране счёта у не вошедших `countsInBalance: false`.
- Счёт берётся существующий — видимый, в той же валюте, с тем же названием, иначе того же вида (у
  перенесённого пользователя это его «Карта» со всей историей); нет такого — создаётся. После первого запуска
  у пользователя есть все три счёта, даже с нулями («Начать с нуля» — пустое тело).
- Три счёта встают первыми в порядке экрана и досок — Наличные, Карта, Доллары (`sortOrder` 10, 20, 30;
  FT-137); другие счета, если есть, идут за ними в прежнем порядке. Порядок ставит первый запуск: у тех, кто
  его уже прошёл, данные не правятся.
- Затем в настройках ставится `onboardedAt` — экран больше не показывается. Ответ `200`: то же, что
  `GET /api/accounts`, и `onboardedAt`.
- Ошибки: сумма не целое число от 0, лишнее поле, тело не объект — `400`; первый запуск уже пройден — `409`
  (остатки дальше правятся на экране счетов, FT-118); без авторизации — `401`.

Ошибки: имя пустое или длиннее 40, `kind`/`currency` не из списка, остаток не целый, дата не `YYYY-MM-DD`,
скрыть последний видимый счёт — `400`; имя уже есть (без учёта регистра) или смена валюты у счёта с
операциями — `409`; чужой счёт — `404`. Операции — записи и перемещения, удалённые перемещения тоже
(их можно восстановить).

## Перемещения: перевод, обмен, корректировка (FT-104)

Перемещение меняет остатки и только их: в доходы, расходы, аналитику, итоги дня, ревизию и цели оно
не попадает. Хранится в `account_moves`.

`POST /api/moves` → `201` и перемещение:

| `kind` | Тело | Что сохраняется |
|---|---|---|
| `transfer` | `fromAccountId`, `toAccountId` (одна валюта), `amountMinor`, `date?`, `note?` | `fromAmountMinor` = `toAmountMinor` |
| `exchange` | `fromAccountId`, `toAccountId` (разные валюты), `fromAmountMinor` (отдал), `toAmountMinor` (получил), `date?`, `note?` | `dealRateMinor` — курс сделки (сумы×100 за $1, из двух сумм, округление половины вверх); `cbuRateMinor` — курс ЦБ на дату или `null`, если его нет |
| `adjustment` | `accountId`, `balanceMinor` — сколько на счёте на самом деле, `note?` | `toAmountMinor` — разница с посчитанным остатком со знаком; дата — сегодня |

```json
{ "id": "…", "kind": "exchange", "fromAccountId": "…", "toAccountId": "…",
  "fromAmountMinor": 10000, "toAmountMinor": 126000000, "dealRateMinor": 1260000, "cbuRateMinor": 1265000,
  "date": "2026-10-12", "note": null, "createdAt": "…", "deletedAt": null, "userId": "…" }
```

Ошибки `400`: у пользователя один видимый счёт — «A transfer needs a second visible account: add one first»
(`field: toAccountId`); счёт скрыт; счета совпадают; валюты разные у перевода («that is an exchange») или
одинаковые у обмена («that is a transfer»); сумма не целое положительное; дата не `YYYY-MM-DD` или раньше
даты открытия одного из счетов; заметка длиннее 200; корректировка до того же остатка («The balance already
matches»). Чужой счёт — `404`. Денег на счёте сервер не проверяет: остаток может уйти в минус, форма
предупреждает сама.

`DELETE /api/moves/:id` — мягкое удаление, остатки обоих счетов возвращаются; `POST /api/moves/:id/restore`
— обратно. Оба отвечают перемещением (`deletedAt` — дата или `null`), повтор ничего не меняет. Чужое — `404`.

`GET /api/accounts/:id/operations?from&to` — экран счёта: счёт с остатком и операции по дням, новые сверху,
внутри дня — по времени создания.

```json
{
  "account": { "id": "…", "name": "Карта", "balanceMinor": -32500000, "…": "…" },
  "days": [
    { "date": "2026-10-12", "operations": [
      { "type": "move", "id": "…", "kind": "transfer", "amountMinor": -30000000, "countsInBalance": true,
        "counterpart": { "id": "…", "name": "Наличные", "currency": "UZS" }, "move": { "…": "…" } },
      { "type": "record", "id": "…", "amountMinor": -2500000, "countsInBalance": true, "record": { "…": "…" } }
    ] }
  ],
  "earlierDate": "2026-08-14"
}
```

`account.hasOperations` (FT-118) — у счёта есть записи или перемещения, удалённые тоже: валюту сменить уже нельзя,
даже если в `days` пусто. Экран счёта по нему решает, показать ли «Сумы / Доллары» в «Изменить».

`earlierDate` (FT-118) — с `from`: день самой новой операции раньше `from`, `null` — раньше ничего нет (и всегда
`null` без `from`). Экран счёта читает окнами по 60 дней: сначала `from` = 59 дней назад, следующее окно —
`to=earlierDate`, `from` на 59 дней раньше; поэтому ни одно окно, кроме первого, не приходит пустым.

`amountMinor` — изменение остатка этого счёта со знаком. `countsInBalance: false` — операция раньше даты
открытия счёта, операция дня открытия, записанная до `openingAt` (FT-163), или запись в другой валюте («55$» на
сумовом счёте). `record` — запись в том же виде, что в
истории; `counterpart` — второй счёт перевода или обмена (`null` у корректировки).

## Курс доллара (FT-102)

`GET /api/rates/usd`

```json
{
  "effective": { "rateMinor": 1285037, "source": "cbu", "date": "2026-10-16" },
  "cbu": { "rateMinor": 1285037, "date": "2026-10-16", "fetchedAt": "2026-10-16T04:00:12.000Z" },
  "own": null
}
```

| Поле | Что |
|---|---|
| `rateMinor` | сумы×100 за 1 доллар: `1285037` = 12 850,37 сум |
| `effective` | курс, который действует: свой, если задан, иначе последний курс ЦБ; `null`, пока курса нет совсем |
| `cbu.date` | на какую дату курс ЦБ. Если ЦБ не ответил, действует последний известный — интерфейс называет его дату |
| `own.since` | с какой даты действует свой курс |

`PUT /api/rates/usd/own` — `{ rateMinor, since? }`, целое от 100 до 100 000 000 → свой курс с сегодняшнего дня.
`since` (FT-119) — `YYYY-MM-DD` не позже сегодняшнего: «Отменить» после смены курса возвращает прежний свой курс с
его датой («Свой с 10 окт»). Ошибка `400` — курс не из диапазона или `since` не дата / в будущем.
`DELETE /api/rates/usd/own` — вернуться к курсу ЦБ («Вернуть курс ЦБ»). Ответ обоих — как у `GET`.
Шторка «Курс доллара» (FT-119) принимает свой курс от 1 000 до 100 000 сум, целыми сумами.

Курс ЦБ загружается при старте и затем раз в час, пока не появится курс на сегодня
(`https://cbu.uz/ru/arkhiv-kursov-valyut/json/USD/{дата}/`). Пересчёт долларов в сумы — по действующему
курсу на момент показа, с округлением до целых сум; у обмена (FT-104) свой курс сделки.

## Категории (FT-099)

`GET /api/categories[?type=expense|income]` — все категории пользователя, скрытые тоже; при первом обращении
создаются 8 + 8 стартовых. Порядок: по типу, затем `sortOrder`; «Другое» всегда последняя.

```json
{ "id": "…", "type": "expense", "name": "Кафе", "color": "rose", "isHidden": false,
  "isOther": false, "sortOrder": 20, "presetKey": "cafe", "userId": "…" }
```

| Поле | Что |
|---|---|
| `color` | один из 8 пастельных токенов: `peach`, `rose`, `sky`, `sand`, `lilac`, `mint`, `butter`, `mist` |
| `isOther` | «Другое» своего типа: сюда попадает всё нераспознанное; не скрывается |
| `presetKey` | ключ стартовой категории, не меняется при переименовании; `null` у своих |

`POST /api/categories` — `{ type, name, color }` → `201`. Своя категория встаёт перед «Другое».

`PATCH /api/categories/:id` — любое из `{ name, color, isHidden }`. Тип не меняется.

`DELETE /api/categories/:id` (FT-127) — «Отменить» сразу после «Категория добавлена»: удаляется только своя
категория (не стартовая и не «Другое» — `400`), в которую не попала ни одна запись, удалённые тоже — иначе `409`:
такая категория скрывается, а не удаляется. Проверка и удаление — одним запросом. Ответ — `{ "id": "…" }`.

Ошибки: имя пустое или длиннее 40 символов, цвет не из списка, скрыть «Другое», чужое поле — `400`;
имя уже есть у категории того же типа (без учёта регистра, «ё» = «е») — `409`; чужая категория — `404`.

Скрытая категория пропадает из выбора и из промпта ИИ; её записи остаются в истории (API-фильтр `categoryIds`
принимает и скрытую) и в аналитике месяца и категории — это проверяет `tests/categoriesScreen.test.ts` (FT-127).

## Настройки (FT-098)

`GET /api/settings` → настройки; пользователь, который ничего не менял, получает значения по умолчанию
(строка в базе не создаётся).

`PATCH /api/settings` — одно или несколько полей; неизвестное поле — `400`.

| Поле | Значения | По умолчанию |
|---|---|---|
| `theme` | `telegram`, `light`, `dark` | `telegram` |
| `dailySummaryEnabled` | `true`, `false` | `true` |
| `dailySummaryTime` | `20:00`, `21:00`, `22:00`, `23:00` | `21:00` |
| `auditEnabled` | `true`, `false` | `true` |
| `auditTime` | `09:00`, `10:00`, `12:00`, `19:00` (1-го числа) | `10:00` |
| `goalAlertsEnabled` | `true`, `false` | `true` |
| `onboardedAt` | ISO-момент или `null` | `null` — показать первый запуск |
| `receiptTipsSeen` | 0…3 | 0 |
| `auditInviteSnoozedUntil` | `YYYY-MM-DD` или `null` | `null` |
| `displayCurrency` | `UZS`, `USD` — «Сум / USD» на главной (FT-137): в чём показаны карточка баланса и плитки месяца. Это выбор, а не факт: без курса главная показывает сумы, а выбор ждёт курса | `UZS` |

| `defaultAccountId` | id видимого счёта пользователя в сумах или `null` (FT-101, FT-149); долларовый или скрытый — `400` | `null` — первый видимый счёт в сумах |

Только для чтения: `userId`, `fxOwnRateMinor`, `fxOwnSince` — свой курс задаётся через `/api/rates/usd/own`.

Кто пишет и кто читает (FT-125). «Ещё» меняет `theme` и уведомления бота по одному полю за нажатие. `theme` —
выбор пользователя для всех его устройств: webapp показывает его сразу, до ответа, и держит копию на устройстве
только для первого кадра. `dailySummaryEnabled` и `dailySummaryTime` планировщик сводки (FT-124) читает при каждом
взгляде на часы — изменение действует в тот же вечер, а сводка, которая уже ушла, не повторяется. `auditEnabled`,
`auditTime` и `goalAlertsEnabled` так же читают напоминания бота (FT-133): ревизия 1-го числа в `auditTime`, цели и
подписки — пока включено `goalAlertsEnabled`; выключенное не шлёт ничего, включённое снова шлёт то, что ещё не ушло.

`defaultAccountId` (FT-149) меняет строка «Счёт по умолчанию» в «Ещё» → «Деньги»: в шторке только видимые счета в
сумах — решение Шукура 2026-10-29: запись с «$» и так идёт на долларовый счёт по своей валюте (`accountBook.ts`, выбор
по валюте), поэтому долларовый счёт по умолчанию только пропускался бы. Его читают все записи в сумах без названного счёта: фраза (`POST /api/quick-capture`, бот) — на сервере
(`accountBook.resolveForRecord`); ручной ввод, стартовые чипы и фраза без связи — в webapp из настроек в кэше, поэтому
выбор действует сразу, до ответа. Частый чип (`GET /api/transactions/frequent`) пишет на свой `accountId`, пока тот
виден. Если счёт по умолчанию скрыли, настройка остаётся, а записи идут на первый видимый счёт; строка «Ещё» так и
пишет: «Наличные · счёт «Карта» скрыт». Покажут счёт снова — он снова по умолчанию. Долларовый счёт, сохранённый до
FT-149, тоже остаётся в настройке: записи в сумах идут на первый видимый счёт в сумах, строка — «Наличные · счёт
«Доллары» не в сумах».

## Выгрузка всех записей (FT-126)

«Скачать все записи» в «Ещё». Обе формы дают один и тот же файл `kapelka-<сегодня>.csv`: все неудалённые и
неархивные записи и все неудалённые перемещения пользователя, от старых к новым.

| Маршрут | Где | Ответ |
|---|---|---|
| `GET /api/export` | в браузере | сам файл: `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="kapelka-2026-10-14.csv"`, `X-Export-Count` — сколько в нём записей и перемещений |
| `POST /api/export/chat` | в Telegram | файл уходит в личный чат с ботом (`sendDocument`, чат — Telegram id из авторизации) с подписью «205 записей на 14 октября — таблица CSV, её откроет Excel или Google Таблицы.»; ответ `{ fileName, count }`. При `count: 0` файл не отправляется |

Файл — для Excel и Google Таблиц на русском: UTF-8 с BOM, столбцы через `;`, строки через CRLF, десятичная
запятая. Столбцы: `Дата;Тип;Сумма;Валюта;Счёт;Категория;Заметка;Курс`.

| Строка | Тип | Сумма | Счёт | Категория | Курс |
|---|---|---|---|---|---|
| запись | `Расход` / `Доход` | расход со знаком «-», доход без знака, в валюте записи: `-24000`, `-12,50` | счёт записи | её текущее название | — |
| перевод | `Перевод` | две строки: `-сумма` на счёте «откуда» и `сумма` на счёте «куда» | | — | — |
| обмен | `Обмен` | две строки, каждая в валюте своего счёта | | — | курс сделки, сумы за $1: `12600` |
| корректировка | `Корректировка` | разница со знаком | её счёт | — | — |

Сумма столбца «Сумма» по счёту — то, что записи и перемещения сделали с его остатком. Перевод считается одним в
`count`, хотя занимает две строки. Текст, который начинается с `=`, `+`, `-` или `@`, пишется с апострофом — Excel
не примет заметку за формулу.

Ошибки `POST /api/export/chat`: выгрузка этого пользователя уже идёт — `409` (второй файл не отправляется); бот не
может написать пользователю (заблокирован, чат не начат) — `422 BOT_CHAT_CLOSED`; Telegram не ответил или токена
бота нет — `502`.

## Вход в браузере через бота (FT-128)

Решение Д4: гостевого режима нет, в браузере входят тем же аккаунтом Telegram. Пароля нет: страница получает
одноразовую ссылку на бота, бот спрашивает «Подтвердить» / «Это не я», страница ждёт и открывается сама.
Секреты браузера живут только в httpOnly-cookie (SameSite=Lax, Secure по HTTPS), в теле ответа их нет; сервер хранит
их хеши (`login_tokens`).

| Маршрут | Что | Ответ |
|---|---|---|
| `POST /api/auth/web-login` | «Войти через Telegram» | `201 { status: 'pending', link, expiresAt }`: `link` — `https://t.me/<bot>?start=login_<token>`, ссылка живёт 5 минут; cookie `daftar_login` (`Path=/api/auth`, 10 минут). Бот неизвестен (нет `TG_BOT_USERNAME`, Telegram не ответил) — `503 LOGIN_UNAVAILABLE`. 10 ссылок с адреса за 15 минут, дальше `429` |
| `GET /api/auth/web-login` | как идёт вход этого браузера (страница спрашивает раз в 3 секунды и сразу, когда к ней вернулись) | `{ status: 'pending', link, expiresAt }` · `{ status: 'confirmed' }` — нажали «Подтвердить», пора взять сессию · `{ status: 'rejected' }` — «Это не я»; этот ответ стирает `daftar_login`, так что после перезагрузки страница его не повторяет · `{ status: 'expired' }` — 5 минут прошли · `{ status: 'none' }` — входа нет (другой браузер, отменён, уже стал сессией) |
| `DELETE /api/auth/web-login` | «Отменить вход» | `{ status: 'none' }`, cookie стирается; бот на эту ссылку отвечает «Ссылка для входа устарела» |
| `POST /api/auth/session` | подтверждённый вход становится сессией браузера | `201 { user: { telegramId, firstName, username } }`, cookie `daftar_session` (`Path=/api`, 30 дней), `daftar_login` стирается. Вход не подтверждён, уже взят или с «Подтвердить» прошло больше 5 минут — `409 LOGIN_NOT_CONFIRMED` |
| `GET /api/auth/session` | кто вошёл (для «Аккаунт» в «Ещё») | `{ user: { telegramId, firstName, username } }`; без входа — `401` |
| `DELETE /api/auth/session` | «Выйти» — только в этом браузере, записи остаются | `{ signedOut: true }`, cookie стирается, сессия на сервере закрыта: та же cookie больше не пускает |

Бот: ссылка открывает чат, «Запустить» шлёт `/start login_<token>`. Вход привязывается к тому, кто открыл ссылку;
бот пишет «Вход в Kapelka из браузера», браузер и систему из User-Agent («Chrome · Windows») и время запроса по часам
пользователя, кнопки `login:ok:<id>` / `login:no:<id>`. Ответ заменяет вопрос: «Вход подтверждён» с «Вернуться в
браузер ↗» (кнопка — только при HTTPS-адресе `WEB_APP_URL`), «Вход отклонён», через 5 минут — «Вход не
подтвердили». Чужая, использованная, отменённая или неизвестная ссылка — «Ссылка для входа устарела». Первый ответ
окончательный.

Сессию читает `webSessionMiddleware` до всех маршрутов. Заголовок `Authorization` (Mini App) важнее cookie; общий
лимит запросов считает сессию пользователем, как initData (600 за 15 минут). 401 вне Telegram webapp понимает как
конец сессии и показывает экран входа; при этом и при «Выйти» он забывает ответы API в кеше service worker
(`api-cache`): маршруты вроде `/api/accounts` не называют пользователя.

Вкладки одного браузера делят cookie. Если вход, которого ждала вкладка, взяла другая (бот открывает приложение
кнопкой «Вернуться в браузер ↗» в новой вкладке), ждущая вкладка получает `409` на `POST /api/auth/session` или
`none` на опросе — и тогда читает `GET /api/auth/session`: сессия есть — открывает приложение. На начальном экране и
на «Вход не подтвердили» страница читает сессию, когда к вкладке вернулись.

Строки `login_tokens` не копятся: каждая новая ссылка удаляет входы, чья ссылка и, если вход стал сессией, срок
сессии закончились больше 7 дней назад (`LOGIN_ROW_KEEP_MS`).

## Ревизия трат и цели (FT-131)

Правила кандидатов — FT-130 (`design-system.md`, «Ревизия трат»); здесь — как ревизия хранится, решается и
становится целями. Пользователь — только из авторизации; без неё — `401`. «Сегодня» — день по Ташкенту.

| Маршрут | Что |
|---|---|
| `GET /api/audits/current` | ревизия прошлого месяца (в октябре — сентября); при первом запросе открывается, до первой отметки или «Готово» кандидаты находятся заново при каждом запросе |
| `PATCH /api/audits/:id/candidates/:candidateId` | «Нужно / Лишнее» и цель одной траты; ответ — ревизия целиком |
| `POST /api/audits/:id/finish` | «Готово»; ответ — ревизия с целями |
| `GET /api/goals` | цели, которые идут сегодня: «Цели после ревизии» на главной |
| `PATCH /api/goals/:id` | подписка: «Уже отменено», «Напомнить» или снять ответ; ответ — цель |

**Ревизия** (`audits`, одна на пользователя и месяц) открывается при первом запросе. Состав чтением не фиксируется
(FT-142): пока в ревизии нет ни одной отметки и не нажато «Готово», каждый `GET /api/audits/current` находит кандидатов
заново — запись за тот месяц, добавленная после первого чтения (приглашение приходит 1-го, а вчерашнее могли записать
позже), в ревизию входит. Та же трата сохраняет свой `id` (тот же ключ или `isSameAuditSpending`, перенесённая — только
с перенесённой), поэтому отметка, отправленная по прочитанному раньше, находит свою трату; новая трата получает новый
`id`, пропавшая уходит из ревизии (её отметка — `404`). Первая отметка (`PATCH`, любая, в том числе выбор цели) или
«Готово» замораживают состав навсегда — и когда отметку потом сняли: дальше запись за тот месяц ревизию не трогает.
Два первых запроса сразу открывают одну ревизию; отметка, пришедшая одновременно с чтением, не теряется (версия строки).

Пока месяц не записан целиком (FT-130: запись началась не позже его 3-го дня), ревизии нет — `state: "too_early"`,
строка не создаётся, `firstAuditOn` говорит, когда откроется первая («Первая ревизия — 1 ноября»; без записей —
`null`), `firstRecordDate` — день первой записи. Открытая ревизия остаётся открытой, даже если записи потом удалили.

К найденному правилами в новой ревизии добавляется и вычитается:
- **неразобранное** в ревизии прошлого месяца приходит в эту (`carriedFrom: "2026-09"`) со своими числами и
  причиной, после найденного, крупные сверху — если правила не нашли ту же трату снова (тогда она новая). Приходит
  один раз: оставленная снова, она вернётся, только если её найдут правила. Из более старой ревизии — не приходит;
- **«Нужно»** — трата не предлагается, пока заметно не вырастет: последнее решение о ней в прошлых ревизиях —
  «Нужно», и месяц теперь меньше чем в 1,5 раза больше тогдашнего (`AUDIT_DECISION_RULES.needAgainRatio`); подписка
  и тариф — пока не подорожали больше чем на 10%. Та же трата в двух ревизиях — `isSameAuditSpending`;
- **«Уже отменено»** — сервис не предлагается, если его последнее списание не позже дня, когда это нажали.

```json
{
  "id": "…", "month": "2026-09", "today": "2026-10-14", "state": "done", "firstRecordDate": null, "firstAuditOn": null,
```

- `state`: `too_early`, `open` (до «Готово»), `done` (после; «Изменить отметки» оставляет `done`).
- У кандидата `decision` — `need`, `extra` или `null`; `goalChoice` — выбранное «Вдвое меньше» (`half`) или
  «Отказаться» (`drop`), хранится и при снятой отметке; `goal` — цель, которую решение даёт сейчас: повторяющееся
  лишнее — `half` (по умолчанию) или `drop`, подписка и платный тариф — `cancel`, разовая покупка, нужное и
  неразобранное — `null`. `halfLimitMinor` — лимит «Вдвое меньше» (половина месяца до тысячи сум), `null` у подписки
  и разовой покупки; `savingMinor` — что цель экономит в месяц сейчас.
- `summary`: `count` — все кандидаты, и перенесённые («Разобрано 2 из 6»), `marked` — разобрано, `left` — уйдут в
  следующую ревизию. `totalMinor` — «— 2 319 000 сум за сентябрь» и `wastedMinor` — «на лишнее ушло» (у «Вдвое
  меньше» — только сверх лимита, разовая покупка — целиком) считают **только траты месяца ревизии** (FT-142):
  перенесённые потрачены в своём месяце, их числа отдельно — `carriedCount`, `carriedTotalMinor` (сколько они взяли в
  своём месяце), `carriedWastedMinor` (что из них ушло на лишнее по нынешним отметкам). `planMinor` — экономия в месяц
  с этого дня, и по перенесённым целям («Отказаться» и «Отменить» — весь месяц траты, «Вдвое меньше» — часть сверх
  лимита).

`PATCH /api/audits/:id/candidates/:candidateId` — `{ "decision": "need" | "extra" | null }` и/или
`{ "goal": "half" | "drop" }`; повторное нажатие экран шлёт как `decision: null`. Ничего из двух или другое
значение — `400`; `goal` у подписки, тарифа или разовой покупки — `422`; чужая или неизвестная ревизия, неизвестный
кандидат — `404`; ревизия не текущая (её месяц уже не прошлый) — `409` с `context.reason: "AUDIT_CLOSED"`. Два нажатия сразу не теряют
ни одной отметки (версия строки, запись повторяется). После «Готово» цели меняются сразу: синхронизации целей одной
ревизии идут по очереди, каждая читает ревизию, когда начинает, а перед созданием цели перечитывает решение — трата,
которую тем временем отметили «Нужно», цели не получает (FT-142).

`POST /api/audits/:id/finish` — «Готово»: нужна хотя бы одна отметка (`422`, если кандидаты есть и ни один не
отмечен). Первое нажатие даёт ревизии день (`doneOn`) — с него считаются цели; повторное (после «Изменить отметки»)
день не меняет. Ошибки владельца и закрытой ревизии — как у `PATCH`.

**Цели** (`goals`) — по одной на лишнюю повторяющуюся трату, со дня ревизии до конца его месяца; следующая
ревизия ставит цели следующего месяца. `GET /api/goals` — цели, в чьи дни входит сегодня, крупные сверху:

```json
{
  "today": "2026-10-14", "startsOn": "2026-10-14", "endsOn": "2026-10-31", "planMinor": 81400000,
  "comparison": { "amountMinor": 36540000, "previousMinor": 77400000, "percent": -53 },
  "goals": [
    { "id": "…", "auditId": "…", "kind": "half", "name": "Такси", "categoryId": "…", "categoryName": "Транспорт",
      "serviceKey": null, "serviceKind": null, "monthlyMinor": 34900000, "limitMinor": 17500000, "savingMinor": 17400000,
      "startsOn": "2026-10-14", "endsOn": "2026-10-31", "periodLimitMinor": 10200000, "spentMinor": 2400000, "count": 1,
      "comparison": { "from": "2026-10-01", "amountMinor": 26240000, "previousFrom": "2026-09-01",

    { "id": "…", "kind": "cancel", "name": "Кинопоиск", "serviceKey": "kinopoisk", "serviceKind": "subscription", "monthlyMinor": 5000000, "limitMinor": 0, "savingMinor": 5000000,

      "subscription": { "state": null, "lastChargeOn": "2026-10-03", "nextChargeOn": "2026-11-03", "remindOn": "2026-11-02", "chargeMinor": 5000000 } }

```

- **Лимит с дня ревизии** — `periodLimitMinor`: лимит месяца × оставшиеся дни (день ревизии включительно) / дни
  месяца, до тысячи сум: 175 000 × 18 / 31 → 102 000 («Потрачено 24 000 из 102 000 сум до 31 октября»). У
  «Отказаться» и «Отменить» — 0.
- `spentMinor`, `count` — траты по цели с дня ревизии до конца месяца (запись с будущей датой этого месяца входит,
  как в плитках главной). Трата — та же, что в ревизии: категория и группа заметок («Такси домой» — это «Такси») или
  сервис каталога в любой категории; доллары — по действующему курсу; не входят доходы, переводы, долги и записи на
  проверке.
- `comparison` — с 1-го числа против тех же дней прошлого месяца (до сегодняшнего числа, у короткого месяца — до его
  конца); `percent` — целые проценты со знаком. `null` у подписки и когда в те же дни прошлого месяца этой траты не
  было. Общая строка (`comparison` наверху) — сумма целей, у которых сравнение есть.
- `serviceKind` — у `cancel`, что отменять (FT-142): `subscription` — подписка («цель: отменить», «Уже отменено»,
  «Отмените в самом сервисе до этой даты.», «Отменено — больше не спишут»), `tariff` — платный тариф оператора
  («цель: отключить», «Уже отключено», «Отключите у оператора до этой даты.», «Отключено — больше не спишут»). Берётся
  из каталога сервисов по `serviceKey` (сервис, которого в каталоге больше нет, — подписка); у других целей `null`. У
  кандидата то же говорит `kind` (`subscription` / `tariff`).
- `subscription` — у `cancel`: последнее списание (то, что видела ревизия, или позже — до сегодня), следующее —
  через месяц в тот же день (31-е в коротком месяце — его последний день; годовая — через 12 месяцев), `remindOn` —
  день напоминания: сохранённый после «Напомнить», иначе день до списания, но не раньше сегодня; после «Уже
  отменено» — `null`. `chargeMinor` — сколько спишут (FT-133, «3 ноября Кинопоиск спишет 50 000 сум»): последнее
  списание как записано (всё, что в тот день), без записи — месяц цели × месяцы между списаниями; `null` до первого
  списания.

`PATCH /api/goals/:id` — `{ "subscription": "cancelled" | "remind" | null }`: «Уже отменено» запоминает день
(`cancelled_on`), «Напомнить» — день, когда бот напомнит о списании (FT-133), `null` снимает ответ. Без поля или другое
значение — `400`; цель не подписка — `422`; чужая — `404`.
