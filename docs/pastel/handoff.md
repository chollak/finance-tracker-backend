## Ждёт решения Шукура

1. **FT-088** — вывод по голосу после проверки на устройствах → `docs/tasks/decisions.md`; от него зависит FT-117.
2. **FT-089** — спайк чеков: нужны 10 настоящих чеков и ключ модели с vision; от него зависят FT-134 и FT-135.
3. **FT-108** — backfill `semanticType`: пересобрать превью FT-045 (`scripts/preview-semantic-backfill.ts`),
   показать список, применить только одобренное. Это правка данных — без просмотра не делать.
4. **Старые даты.** Быстрое добавление в боте до FT-100 сохраняло в `date` полный момент
   («2026-10-14T05:30:00.000Z»). Код теперь это выдерживает (история, операции счёта), но такие записи не
   попадают в отчёты, где конец периода — этот день. Нормализовать — отдельной миграцией после просмотра
   списка: это тоже правка данных.
5. **Перевод текстом.** «Перевёл 500 000 на Humo» пишется записью `own_transfer` на счёт по умолчанию (не в
   расходы). Настоящим перемещением между счетами его делает форма перевода (FT-119). Разбирать такие фразы в
   перемещение — отдельное решение.
6. **Старые маршруты берут `userId` из тела** (`POST /api/transactions`, `quick-capture`) — так было до
   вехи. Новые маршруты фазы 2 берут пользователя только из авторизации. Перевести старые — вместе с экранами
   фазы 3, когда их писатели заменятся.
7. **Лимиты free** выключены по умолчанию (Д3, `FREE_LIMITS_ENABLED`); счёт записей идёт.
8. **«Сум / USD» в шапке главной** — решено 2026-10-20 (`docs/tasks/decisions.md`): отдельная задача FT-137
   вместе с порядком счетов «Наличные, Карта, Доллары»; сделано в FT-137.

## Что знать о модели денег

Контракты — [`api.md`](api.md), схема — [`money-model.md`](money-model.md). Коротко:

- Суммы — целые в `amount_minor`; `amount` в ответах остаётся до FT-136.
- У записи есть счёт, валюта и источник. Итоги (аналитика, дашборд, недельный отчёт, `/today`, `/stats`,
  `/week`) считает один `PeriodTotalsService`: доллары по действующему курсу, с сумами как есть не складываются.
- Старые экраны webapp, которые складывают `amount` сами, долларовые записи пока считают «не в счёт»;
  бюджеты (уходят из интерфейса, Д2) их не учитывают и не находят старые записи по статическим id категорий.
- Удаление мягкое, повтор с тем же `clientId` возвращает ту же запись, история — `GET /api/transactions`.
- Пользователи, у которых записи хранятся под Telegram id, а не под UUID, получают свои счета и категории
  под этим id — так же, как раньше получали записи.
